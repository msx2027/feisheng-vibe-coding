# Bounded Development Execution Core

This is the compact all-depth base for `开发执行`. It is sufficient for a mechanical `D0` result and for an eligible bounded `D1` change with one established owner. It never weakens owner closure, test classification, effect authorization, security-impact classification, or fresh verification.

## Bounded D0 Path

1. Confirm the exact requested result, target, transformation, active exclusions, and authorization boundary.
2. Read the target, its direct owner context, the narrow existing check or read-back path, and overlapping Git state.
3. Classify depth with `task-risk-gates.md`. Continue on this compact path only when the result is genuinely `D0`; otherwise load the conditional owners named by `routes-index.md` before editing.
4. Classify the evidence level with `testing-strategy.md` and the next action with `effect-recovery-gates.md`.
5. Apply the exact transformation at the existing owner. Do not introduce semantic choices, new owners, compatibility paths, fallbacks, abstractions, or unrelated cleanup.
6. Run the selected fresh check, inspect the exact diff or read-back, and report verified and unverified planes separately.

Stop the D0 path and reclassify before editing when any of these is true:

- the target or transformation must be chosen rather than executed mechanically;
- behavior, shared meaning, a caller/consumer contract, or user-visible structure must be designed;
- the task is not mechanical, a bug needs diagnosis, or several reasonable outcomes remain;
- a protected risk lane, formal materialization, durable truth, release scope, or another conditional owner activates;
- the existing check cannot honestly prove the requested result.

## Bounded D1 Eligibility

Use bounded D1 only when all of these are true:

- task-depth classification is `D1`, with one established owner and no unresolved owner boundary;
- the requested behavior and acceptance are fixed by current truth, reproduction, or an explicit user-visible result;
- discovery can close over the owner, direct consumers, affected tests, current Git state, and active risk/effect boundaries without designing a new cross-owner contract;
- the implementation does not create a new foundation, durable schema, compatibility path, fallback, public contract, or materially different delivery shape;
- the selected test level and fresh verification can prove the change through existing owners; every activated protected lane still loads its unique risk owner.

Eligibility is a compact execution decision, not permission to skip professional judgment. A bounded D1 bug still needs reproduction, one evidence-backed failing boundary, and an affected-test map.

## Bounded D1 Execution

1. Close discovery over the one owner, direct consumers, affected tests, current truth, Git overlap, and exact exclusions. Batch independent read-only discovery while preserving owner closure; physical tool-call count is Host telemetry, not portable correctness.
2. Classify the test gate in `testing-strategy.md`. For an ordinary `D1` with no protected lane, follow the project's existing test posture (`T1`; extend an existing suite if one covers the owner, otherwise add no new test code). When `T2` applies, load `testing-execution-gates.md`, add the smallest owner-boundary test, and observe RED before production code.
3. Classify security impact and the next action effect. Load conditional risk/effect owners before their boundary is crossed; do not infer write, Git, external, destructive, credential, production, or release authority from local-edit authorization.
4. Implement at the established owner, then update only required thin consumers. Preserve explicit exclusions and unrelated dirty work.
5. Run targeted checks plus the affected regression set, inspect the exact diff/read-back, and collect fresh verification before any completion claim. When the change touched a route, handler, middleware, auth wiring, CLI/job entry, or page entry, also run Runtime Boundary Verification from `testing-strategy.md` against the local runtime; a green owner test alone leaves that plane `未验证`.

## Exit Bounded D1

Exit Bounded D1 and load `routes-feature.md` plus `engineering-execution.md` before further owner code when owner closure fails, the behavior or delivery shape needs design, more than one semantic owner changes, the RED cannot be expressed at the owner boundary, a third-party/production/release contract becomes material, or fresh evidence contradicts the bounded hypothesis. `D2`/`D3` always exit this compact path.

## Pending Operation Entry

Before starting a command or tool operation that may yield a running handle, when any pending operation already exists, or when context degrades or handoff begins, load `execution-liveness.md`. Do not emit final or handoff while a pending operation lacks a terminal, canceled, degraded, or explicitly blocked decision allowed by that owner.

## Compact Invariants

- Current files, direct runtime evidence, and Git state beat memory or old chat.
- One concept has one owner; edit generated output only through its source and generator.
- Preserve every explicit exclusion and all unrelated dirty work.
- Test classification is mandatory even when no new test code is needed; ordinary `D1` follows the project's existing test posture and does not introduce a test framework.
- No fresh verification, no completion claim. A changed request or command entry also needs Runtime Boundary Verification (`testing-strategy.md`).
- Staging, commit, push, deployment, publication, production access, destructive data work, and credential use require their own exact authorization; a local edit never implies them.

The complete route procedure, professional-design gates, Delivery Shape Lock, debugging ladder, anti-pattern catalog, verification matrix, and write-back rules remain in the conditional owners named by the selected exact route projection; do not recreate them here.
