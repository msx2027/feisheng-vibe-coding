# AGENTS.md

任何时候使用中文，除非用户明确要求英文输出。

## 项目阶段

本项目处于从零启动或空项目启动阶段。AI 不能直接写功能代码、直接选框架、直接搭页面。必须先写清产品边界和第一闭环，审计完整技术决策证据，由 AI 给出唯一主技术栈与架构组合，用户只确认产品可见结果和成本、停机、数据、迁移或不可逆后果。只有进入 `implementation_ready` 并把当前具体 owner 和验收方式写入 `dev-docs/` 后才能实施。

## 核心规则

- 架构优先、设计优先、真源优先、严格验收。
- 先读 `dev-docs/README.md` 指向的当前真源，再做判断。
- 给非技术用户一个主推荐，不给多个平级方案让用户猜。
- 技术选型与架构必须基于项目真源、架构驱动因素、可检验质量场景、平台能力、部署目标、第三方依赖、维护能力和商业约束。
- AI 先审计现行设计文档和代码证据，再联网查当前官方文档、支持矩阵、版本、许可证、安全和部署约束；不能凭模型记忆定案。
- 信息不明、真源冲突或关键能力无法评估时，每次只问一个会改变决策的产品问题，直到证据充分；不得给最终选型或把候选写成真源。
- 用户只确认可见产品结果、成本、交付、停机、数据和不可逆影响；AI 必须自己决定技术栈、框架和架构组合，不让用户选技术名词。
- MVP 是当前交付边界，不是架构上限；不得堵死有证据确认的下一阶段能力，也不得为未确认未来增加当前复杂度。
- 前端必须先有设计方向、token 真源、组件复用规则和样式漂移防线。
- 后端必须先有责任边界、API 合同、数据 owner、权限/安全边界和验证方式。
- 共享业务语义只能有一个 owner。UI、controller、adapter 只做展示或映射，不能私自拥有业务规则。
- 禁止补丁式开发：不得用散落 if、临时兼容、硬编码、mock、假成功、sleep、全局 flag 绕过架构问题。
- 禁止无意义兼容。旧字段、旧接口、旧页面、旧产品概念会污染当前主线时，先让用户做取舍。
- 用户纠正先分类为产品决定、现场事实、技术方案或偏好反馈：用户拥有产品结果，事实由当前证据裁决，技术方案由 AI 基于真源和 owner 合同判断。只有已确认的产品否定项或经证据判定错误的技术概念才能删除，不能为了迎合换名字保留。
- 情绪、重复施压或批评只触发重新审计，不能替代技术证据或改变结论；说“你说得对”前必须说明争议命题和证据判定。
- 任何缺失证据都标记为 `未验证`，不能包装成已完成。

## UI 设计与实现红线

- 设计前先读当前项目的布局、token、组件、图标、主题和断点真源；新项目先建立最小视觉基础，不凭单张页面发明完整设计系统。
- UI 原型必须归档到当前内部真源根的 `design/`，记录状态、版本和批准证据；已批准版本不得覆盖。
- 未记录为 `approved_version` 的原型不得进入实现。
- 不得用整张设计图、截图切片或透明热区冒充可交互 UI；文字、按钮、表单和导航必须使用真实语义元素。
- 实现优先复用现有组件、token、图标和主题机制；设计稿的视觉意图不能成为新建并行 UI 体系的理由。

## 测试与验证

- 任何实现改动前都必须先分类测试门禁：非行为改动做针对验证，已有失败门直接复用；登录、权限、跨用户数据、金钱、持久数据结构、公共接口合同这些保护边界上稳定可自动化的行为严格先 RED 再 GREEN；普通改动跟随项目现状，被改模块已有测试就补一条并跑绿，没有就不新建测试、不引入测试框架；无法可信自动化的真实边界必须留可重复的前后证据。
- 改动路由、handler、中间件、鉴权接线、CLI/任务入口或页面入口后，必须在本地跑起项目，用真实请求走一遍改动的入口，并按安全影响清单命中项发对应的负向请求（无凭证、他人身份、篡改服务端字段、畸形输入），记录状态码与脱敏响应；单元测试通过不能替代这一步，跑不了就写明阻塞并标 `未验证`，不得称完成。
- 测试必须验证真实行为和 owner 合同；禁止为凑覆盖率测 mock 自己、为测试污染生产 API、用零测试通过或无关绿色套件冒充验证。

## 启动顺序

```text
产品边界
  -> 第一闭环
  -> 功能拆分和不做什么
  -> 架构驱动因素和质量场景
  -> 技术栈、框架与架构组合决策
  -> 当前具体架构和 owner map
  -> agent 宪法正式化
  -> 第一阶段实施真源
  -> 子阶段开发
  -> 验收和 Git checkpoint
```

- 仅当多个 owner 会漂移、有序迁移无法一次关闭，或用户明确需要持久交接时，使用一份 `sliver-stage/v2` 当前阶段真源；计划完成后过 `plan`，修改 owner 前过 `execute`，验证和回写后过 `closeout`。深度和风险本身不触发文档，收尾不自动授权下一子阶段。

## 必须先问清楚

- 谁会第一个使用这个项目。
- 第一版必须完成哪一个完整动作。
- 第一版明确不做什么。
- 是否涉及登录、角色、支付、上传、敏感数据、第三方服务、本地系统能力或生产环境。
- 用户能接受的上线方式、预算、维护方式和交付对象。
- 哪些性能、可靠性、恢复、安全、成本或演进结果真的会改变产品，以及可接受的度量边界。

## Git 和隐私

- 编码前确认真实项目根目录，避免在下载目录、参考项目或混合资料目录初始化项目。
- 第一次提交前先审 `.gitignore`，保护 `.env`、密钥、数据库、本地上传、内部资料、真实案例、商业计划和第三方参考库。
- 如果 `dev-docs/` 是内部资料且不能推送，先确认双仓管理：代码仓忽略 `dev-docs/`，`dev-docs/` 可单独本地 Git。

## 安全红线

- 前端输入不可信；身份、权限、数据归属、金额、权益、状态和数据库写入必须由服务端重新验证。
- 用户输入不得直接进入 SQL、系统命令、HTML 或模板；接口必须限制允许写入的字段。
- 密钥不得写入源码、日志、错误、截图、生成物或 Git 历史。
- 新增或修改安全边界时，必须验证非法参数、未登录、错误角色、跨用户访问、篡改字段和必要的资源上限。
- 重要数据写入必须评估事务、幂等、迁移、备份和回滚。
- 开发和生产环境必须隔离，生产调试模式必须关闭，数据库、缓存和内部管理面不得默认暴露公网。
- 安全审计不等于修复授权；用户只要求检查时先报告风险和证据，未经确认不得扩大修改。
- 未提供本轮安全验证证据，不得声称安全或可以上线；缺失证据必须标记 `未验证`。

## 停止条件

遇到以下情况必须停下并问用户：

- 技术栈、框架、数据库、权限、支付、第三方服务、部署方式要改变。
- 第一闭环、MVP、不做什么或商业边界不清楚。
- 缺少实施真源却准备开发标准或高风险功能。
- 当前证据和用户说法、旧文档、AI 记忆冲突。
- 验证需要真实密钥、生产数据、外部账号、远程部署或破坏性操作。
