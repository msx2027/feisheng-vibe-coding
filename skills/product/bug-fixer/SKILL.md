[DocMap]
    层级：L3 / 关键 Skill
    模块：缺陷修复
    依赖：
    - `.vibe-docs.json`
    - 目标项目需求文档
    - 目标项目开发计划
    - 目标项目当前执行光标
    - 目标项目人工验收记录
    输出：
    - bug 根因
    - 最小修复方案
    - fresh 验证证据
    - 修复后的续接动作

[任务]
    通过系统性调试流程定位 bug 根因并修复。
    一次只修一个问题，每次修改前评估影响范围，修改后做 fresh 验证。
    bug 修复默认按 `execution tier = T3 strict` 执行，不因改动行数少而降级；只有被证实是低风险 typo / copy 才能改走 T0/T1。
    auth、permission、security、database、migration、payment、data loss 风险 bug 默认升级为 T3+ `hazard mode`。
    如果入口请求里还带了“顺手检查有没有漏”“修完再帮我看看”这类次诉求，修复闭环后要把次诉求交还主 Agent 在同一轮继续处理。

[调用上下文]
    `bug-fixer` 可能在这些场景被调用：
    1. 用户直接报 bug：主 Agent 调用 `bug-fixer`，修复后按结果收口。
    2. `code-review` 发现明确行为缺陷：主 Agent 调用 `bug-fixer`，修复后重新回到 `code-review`。
    3. 用户说“修完顺手检查有没有漏”：主 Agent 先调 `bug-fixer` 修主问题；拿到 fresh 证据后，同一轮继续接 `code-review`，不默认停在 `commit`。
    4. 用户说“继续下一步，但这里有个 bug”：主 Agent 先恢复当前任务；如果这个 bug 是当前主线阻塞点，再调 `bug-fixer`；修完后回到原 task 继续。
    5. 用户说“改排序”“默认值不对”这类边界请求，但还没分清是 bug 还是新需求：先由主 Agent 做最少澄清；没澄清前不把新需求当 bug 直接修。

[依赖检查]
    Skill 启动时第一步自动执行。
    必须：
    - 项目代码已存在；无代码时提示先走 `dev-builder`
    - 已有 bug 描述，或 code-review 报告里的明确失败项

    可选：
    - 目标项目需求文档：优先用 `.vibe-docs.json` 的 `productSpec`，默认 `需求文档.md`；legacy `Product-Spec.md` 只作为读取迁移输入，用于核对预期行为，判断是 bug 还是 feature
    - 目标项目开发计划：优先用 `.vibe-docs.json` 的 `devPlan`，默认 `开发计划.md`；legacy `DEV-PLAN.md` 只作为读取迁移输入，用于定位相关 phase 和文件
    - 目标项目人工验收记录：优先用 `.vibe-docs.json` 的 `manualAcceptance`，默认 `验收记录.md`；用于判断修复是否影响已人工验收范围
    - 设计工具或 UI 参考：对照预期界面
    - Playwright 或现有测试基础设施：复现和验证
    - git：追溯近期可疑改动
    - 影响面侦察：跨模块、调用链不清、权限 / 数据 / 本地工具 / UI 流程等 T3 bug，先用 `rg` 沿 callers/callees 与相关测试侦察；有可用的代码图工具时再用

[第一性原则]
    **目标项目上下文加载协议（优先级高于下列文档读取描述）**：存在 `.vibe-docs.json` 时先解析 schema v2、`documentIndex/documents/loadPolicy`，再用 `resolve-target-doc-context.mjs` 从 `documentIndex,currentExecution` 开始，只按复现路径追加受影响的 `productSpec/devPlan/manualAcceptance/interfaceContracts` role；任务胶囊 manifest 通过 `--capsule` 注入。只读取 resolver 返回的 selector，never 被拒绝即阻塞，本 Skill 不得自行使用 `--allow-never`。

    **目标项目文档解析原则**：调试用户目标项目时，先读 `.vibe-docs.json`，再按角色映射定位需求文档、开发计划、当前执行光标和人工验收记录；legacy 英文文档名只作为读取迁移输入。

    **不猜不试**：没有证据就不下结论。先收集、先分析、先假设、再验证。
    **先澄清假设**：如果同一个 bug 存在多个合理解释，不静默押一个方向。先列出当前最可能的 1-3 个假设，并说明各自怎么证伪。
    **需求 / bug 边界先分清**：像“改排序”“文案不对”“默认值不对”这类请求，先核对旧行为、Spec 和最近需求。证据不够时，只问 1 个会改路由的大白话问题，不把新需求当 bug 修。
    **一次一个**：一次只改一个逻辑点。改完验证，再决定是否继续。
    **简洁优先**：默认先修最小且已被证实的根因，不把局部 bug 扩成无关重构；单次 bug 修复不新增未来向抽象、配置层或策略层，除非复现证据证明当前根因需要它。
    **手术式修改**：修复范围必须严格围绕当前 bug，不顺手删无关代码，不顺手重写周边模块；每一行改动都应能追溯到复现证据、修复成功标准或本轮改动造成的最小清理。
    **复合请求先收主诉**：如果入口同时带“修 bug + 顺手检查有没有漏 / 继续下一步”，先把 bug 作为主诉闭环，次诉求记住并交还主 Agent 同轮续接。
    **严格 TDD 铁律**：所有 bug 修复强制 `RED-GREEN-REFACTOR`。修复前先写并运行能稳定复现缺陷的最小 regression test，确认它因用户报告的行为缺陷而正确失败；没有这个 RED，不得修改生产代码。如果修复实现已经先写，删除该实现并从 RED 重新开始，不保留作参考。
    **先造自动化 tight loop**：优先在 public seam、统一接口契约或用户可观察行为边界建立 test、CLI fixture、HTTP integration test 或 Playwright 脚本；curl、日志、trace 和手动复现可用于定位，但不能自行替代失败测试。
    **无 RED 不实施**：没有正确失败的自动化 regression test 时，只能继续补测试 seam、补证据或声明阻塞；不能直接假设根因、不能用“看起来可能是”进入修改。code-review 证据可以作为输入，但仍要转成能复现缺陷的 RED。
    **调用链辅助定位**：T3 bug 默认先判断是否需要先做调用链 / 影响面侦察（`rg` 搜 callers/callees、相关测试与入口；有可用的代码图工具时再用）；侦察结果只是候选根因，必须用复现、源码和验证证据确认。
    **人工验收回归保护**：修 bug 前必须检查 `验收记录.md`。如果修复可能影响已人工验收功能，优先补自动化回归；自动化无法覆盖时，修复交付必须提醒用户只复验受影响路径，并标记 `需回归复验`。
    **无复现 / 无证据不修复**：没有复现路径、日志、断言失败、用户可验证症状或 code-review 证据时，不直接改代码。先补证据；如果只能手动复现，必须写清手动路径并实际跑过一次。无法跑通时声明阻塞，不进入实施修复。
    **例外必须审批**：仅当修复对象属于原型、生成代码或配置文件时，才能在写生产代码前向用户请求例外；必须写清原因、替代验证、风险和 rollback，并获得用户明确批准。无法自动化本身不构成例外资格，手动复现和人工验收也不是自动豁免。
    **GREEN 与 REFACTOR**：正确 RED 后只写让 regression test 通过的最小修复；相关测试全部通过后才能 REFACTOR，且不得新增行为。完成证据必须同时包含本轮 RED 正确失败与 GREEN 通过结果。
    **目标驱动验证**：下手前先写清“修好”到底意味着什么，不能只写“错误没了”。
    **修完不停在 commit**：如果入口请求本来就带 review 次诉求，修完后默认继续 `code-review`，不把“要不要 commit”当默认收口。

[输出风格]
    **语气**：
    - 像医生问诊：先问症状，再查体征，再下诊断，最后开药
    - 每一步都有依据，不用“我改改试试”

    **原则**：
    - x 不在没证据时直接改代码
    - x 不同时改多处而不解释
    - x 不跳过回归验证
    - x 不把 commit 当作复合请求的默认收口
    - v 每次修复附上证据和验证结果
    - v 根因判断要说清推理过程
    - v 修完后明确写清要回 `code-review` 还是回原 task

[调试规则清单]
    [证据收集规则]
        - 完整错误信息与 stack trace
        - 复现步骤
        - RED regression test：必须能说出一个已运行过、能捕捉用户症状且因目标缺陷正确失败的自动化测试命令
        - 定位证据可以来自 curl / HTTP、CLI fixture、Playwright / 浏览器脚本、日志 / trace replay、手动复现协议，但进入修复前仍要形成自动化 RED；例外必须由用户明确批准
        - 每个 tight loop 必须写清输入、执行方式、预期 RED / 用户症状、修后 GREEN / 症状消失标准；无法自动化时记录阻塞状态并停止生产代码修改
        - 期望行为 vs 实际行为
        - 相关环境信息
        - 最近代码变更
        - 控制台、网络、数据库等相关日志

    [假设规则]
        - 每次最多保留 1-3 个假设，按可能性排序
        - 每个假设必须有对应验证方法
        - 先验证最可能的假设
        - 假设被否定后记录原因，不重复验证同一个假设；同一假设、复现路径或验证方向连续失败两次后，必须停止盲试并回到根因分类、入口参数或环境核对，除非出现新证据或用户改变前提
        - 多个假设都成立时，继续补证据，不静默押一个方向

    [修复规则]
        - 一次只改一个文件或一个逻辑点
        - 先写清修复成功标准：什么条件下算“修好”，哪些相关功能要一起回归
        - 进入修改前必须已有正确 RED：regression test 已运行，且因用户报告的行为缺陷而失败
        - 没有正确 RED 时只能补测试 seam、补证据或声明阻塞；不能直接假设根因并修改代码
        - 先检查 `验收记录.md`：本 bug 是否影响已人工验收范围；如影响，写清自动化回归或限定人工复验路径
        - 如果命中 auth、permission、security、database、migration、payment、data loss，先写 Hazard Task Packet
        - 为 bug 先补最小 failing regression test，运行并确认失败原因正确；测试通过、测试自身报错或失败原因不符时先修测试
        - 缺测试基础设施、自动化成本高、外部系统不可控或需求高波动都不是自动豁免；先建立最小 seam，仍不可行时停止生产代码修改
        - 获批例外时记录批准范围、复现路径、替代验证、风险、rollback 和修后回归范围
        - 修改前先评估影响范围
        - 默认优先最小修复，不顺手做无关重构
        - 修后做编译验证、功能验证、回归验证
        - 如果入口还带“顺手检查有没有漏”，修完后把“继续接 `code-review`”写明
        - 如果入口还带“继续下一步”，修完后把“回到当前 task 继续”写明

[调试策略]
    **第一阶段：收集证据**
    - 读完整的错误信息和 stack trace
    - 复现 bug，确认是稳定复现还是偶发
    - 建立 RED feedback loop：写并运行一个能捕捉用户症状的最小自动化 regression test，记录命令、断言、正确失败原因与结果
    - curl / HTTP、CLI fixture、Playwright / 浏览器脚本、日志 / trace replay、手动复现协议可辅助定位；如仍无法形成自动化 RED，停止生产代码修改并报告阻塞
    - 如无法复现、无法运行测试或未获例外批准，先收集更多证据、补测试 seam 或明确阻塞原因；不进入实施修复
    - 检查最近的代码变更
    - 确认问题落在前端、API、数据层还是第三方依赖
    - 追踪数据流和调用链

    **第二阶段：分析模式**
    - 找正常工作的相似功能，对比差异
    - 理解依赖关系
    - 如有目标项目需求文档，核对预期行为

    **第三阶段：假设验证**
    - 基于证据形成 1-3 个假设
    - 用已建立的 tight loop 或同等可复核证据验证最可能的假设；不能靠直接改代码试错替代验证
    - 假设成立就进入修复
    - 假设不成立就记录原因并验证下一个

    **第四阶段：实施修复**
    - 确认 failing regression test 已捕捉到用户症状，且 RED 失败原因正确；获批例外则确认批准范围和替代验证协议已记录
    - 只实施让当前 regression test 通过的单一最小修复
    - 重跑同一个测试与相关回归，记录 GREEN 通过证据；全绿后才允许 REFACTOR，并在整理后再次保持全绿
    - 另做编译、功能和人工验收影响验证，作为 RED/GREEN 之外的补充证据
    - 如修复失败，回到上一阶段重审

[验证阶段]
    修复完成后必须执行：
    1. 编译验证：相关命令能通过
    2. 功能验证：按复现路径确认 bug 不再出现
    3. 回归验证：相关功能仍正常
    4. regression test 必须确认先因正确原因失败、最小修复后通过，并附本轮 RED/GREEN 命令与结果
    5. 仅当修复对象属于原型、生成代码或配置文件，且用户已在写生产代码前明确批准例外时：记录批准依据、原因、手动复现、替代验证、风险、rollback 和回归路径
    5.1. 如影响已人工验收范围：明确自动化覆盖范围；无法覆盖时提醒用户复验受影响路径，并更新 `验收记录.md` 的待复验状态
    6. T3+ 必须附 rollback 方案和 hazard review 续接要求
    7. 如果入口请求里还带“顺手检查有没有漏”：把“继续接 `code-review`”写明，交还主 Agent 同轮续接
    8. 如果入口请求里还带“继续下一步”：把“回到当前 task 继续”写明

[完成阶段]
    向主 Agent 交付时至少包含：
    - **根因**：一句话说清问题为什么发生
    - **修复**：改了哪些文件、做了什么最小改动
    - **验证**：编译 / 功能 / 回归分别怎么验证、结果是什么
    - **人工验收影响**：是否影响 `验收记录.md` 中已确认范围；是否需要用户真实点击 / 操作 / 观察复验
    - **续接动作**：
      - 如果入口带“顺手检查有没有漏”，明确写“下一步继续 `code-review`”
      - 如果入口带“继续下一步”，明确写“下一步回到原 task”
      - 如果都没有，才由主 Agent 决定是否需要其他动作
    - 不把“需要我 commit 吗”当默认结尾
