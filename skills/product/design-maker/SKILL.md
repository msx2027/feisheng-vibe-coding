[任务]
    读取目标项目需求文档和设计简报，通过设计工具 MCP 生成完整的设计交付物。确保 Product Spec 中每个有 UI 的功能都有对应的设计页面，每个页面覆盖所有关键状态变体。这里默认产出的是产品页面设计，不包含 横幅物料、演示稿、CIP 或别的营销物料。

[依赖检测]
    Skill 启动时第一步自动执行。

    必需：
    - 目标项目需求文档 → 优先用 `.vibe-docs.json` 的 `productSpec`，默认 `需求文档.md`；legacy `Product-Spec.md` 只作为读取迁移输入，缺失则提示先调用 /product-spec-builder
    - 目标项目设计简报 → 优先用 `.vibe-docs.json` 的 `designBrief`，新项目默认 `docs/设计简报.md`；若它声明为 Markdown 门面，先读导航，再用 `--markdown` 精确读取本次页面涉及的正文分卷，禁止整目录加载；legacy `Design-Brief.md` 只作为读取迁移输入，缺失则提示先调用 /design-brief-builder
    - 设计工具 MCP → 见下方设计工具检测流程

    设计工具检测流程：
    1. 先执行 [初始化] 中的 tier 分类和 `.vibe-docs.json` 文档加载
    2. 询问用户使用 Pencil 还是 Figma
    3. 若用户选择 Pencil 或目标文件包含 `.pen`：
       - 必须启动桌面 Pencil 客户端；优先使用用户配置的 `PENCIL_EXE`，未配置时要求用户提供本机 Pencil 安装路径
       - MCP 必须使用桌面模式；优先使用用户配置的 `PENCIL_MCP_SERVER`，启动参数固定为 `--app desktop --agent codexCLI`
       - MCP 连接失败时，先检查 Pencil 桌面客户端和 desktop MCP server；严禁 fallback 到 VS Code
    4. 检测对应 MCP 是否已连接
    5. 已连接 → 继续
    6. 未连接 → 尝试连接 MCP，或提示用户连接
    7. 用户未安装对应设计软件 → 提示用户安装后重新调用
    8. 用户选择跳过 → 退出 design-maker，后续流程按无设计稿模式继续

[第一性原则]
    **页面设计主链优先**：这是默认页面设计主链里的“出稿”环节。用户只说前端页面设计时，先把这里做完，再进入 `dev-planner` / `dev-builder`。

    **增强层按需挂载**：只有用户明确要补配色 / 字体 / tokens / design-system / 样式体系时，才拉 `ui-ux-pro-max`、`design-system`、`ui-styling`、`brand` 做页面体系增强。只有用户明确要 critique / audit / polish / 布局 / 排版 / 打磨时，才拉 `impeccable`、`audit`、`critique`、`polish`、`layout`、`typeset` 做二次打磨。

    **其他 impeccable 技能手动调用**：除上面几项核心质量层外，其余 `impeccable` 内建技能只保留手动调用，不默认主动推荐。

    **仓库内建，不走外链**：这里提到的增强 Skill 都按当前仓库 `skills/` 下的内建能力处理，不写本机外部绝对路径。

    **完整覆盖原则**：Product Spec 中每个有 UI 的功能都必须有设计页面。漏一个页面，开发时就少一个参照，后果是开发靠猜。
    **状态完备原则**：每个页面不只有默认态。空状态、加载态、错误态、激活态，有交互的页面必须覆盖关键状态变体。
    **组件先行原则**：先建可复用组件，再用组件拼页面。避免同一个按钮在 10 个页面里画 10 遍、改一次要改 10 处。
    **目标项目文档解析原则**：先读 `.vibe-docs.json`，再按角色映射定位 `docs/需求文档.md`、`docs/设计简报.md` 和 `docs/项目治理/验收记录.md`；正文中出现的 `Product-Spec.md` / `Design-Brief.md` 是 legacy 角色名，新目标项目必须解析到 `docs/` 内的四字中文 `.md`。
    **文档驱动原则**：一切设计决策来自目标项目需求文档和设计简报。不凭个人偏好发挥，不跳出文档范围添加文档未描述的功能。
    **Pencil desktop 原则**：处理 `.pen` 设计文件只允许使用 Pencil desktop 客户端和 desktop MCP server；不允许退回 VS Code、文件编辑器或非 desktop MCP。

[技能]
    - **文档分析**：从 Product Spec 提取所有页面、功能、交互元素；从 Design Brief 提取视觉方向
    - **设计规划**：将提取的信息转化为设计交付清单，列出所有需要设计的页面和变体
    - **组件设计**：使用设计工具 MCP 创建可复用组件系统
    - **页面设计**：使用设计工具 MCP 逐页面生成完整设计
    - **完整性校验**：对照 Product Spec 验证所有页面和状态是否覆盖
    - **人工验收提醒**：设计稿、页面视觉和交互状态完成后，如需要用户真实观察或点击确认，必须提醒用户人工验收；用户确认后写入 `.vibe-docs.json.manualAcceptance` 映射文档，默认 `验收记录.md`
    - **Pencil 操作暗礁**：处理 `.pen` 文件（改节点、替换区域、收编母件、坐标换算、核验截图）前，先读 `references/pencil-pitfalls.md`；该文件只讲操作坑，不改变本文件原则

[设计交付物]
    一套完整的设计稿必须包含以下内容：

    **1. 设计变量**
    从目标项目设计简报提取并设置到设计工具中：
    - 颜色系统：背景色、文字色、品牌色、语义色、标签色
    - 字体系统：字体族、字号层级、字重
    - 间距系统：padding、gap 的常用值
    - 圆角系统：各层级的圆角值

    **2. 可复用组件**
    从 Product Spec 的 UI 布局和功能需求中提取通用组件：
    - 按钮（主要、次要、文字按钮）
    - 输入框
    - 导航项（选中态、未选中态）
    - 卡片
    - 标签/徽章
    - 其他页面中重复出现的元素

    **3. 所有页面**
    Product Spec UI 布局章节中描述的每个页面或视图都必须有对应设计：
    - 从 Product Spec 的 UI 布局、功能需求、用户流程三个章节交叉提取页面列表
    - 每个页面使用可复用组件拼装
    - 布局、间距、内容严格对照 Spec 描述

    **4. 状态变体**
    每个页面根据其交互复杂度覆盖对应状态：
    - 默认态：所有页面必须有
    - 空状态：有数据展示的页面必须有
    - 加载态：有异步操作的页面必须有
    - 错误态：有可能失败的操作必须有
    - 交互变体：同一区域有多种内容切换时，每种内容一个变体

[初始化]
    1. 判定 `execution tier`；设计工具 MCP、`.pen` 文件、Skill / Tool 路由或镜像规则相关变更按 T3+ hazard mode 处理。
    2. 读取目标项目 `.vibe-docs.json`，定位 `productSpec`、`designBrief` 和 `manualAcceptance`；缺失时使用四字中文默认文档名，legacy 英文文档只作为迁移输入。
    3. 执行 [依赖检测] 的设计工具检测流程；Pencil 必须走用户配置的 `PENCIL_EXE` / `PENCIL_MCP_SERVER` 和 `--app desktop --agent codexCLI`。
    4. 加载需求文档和设计简报，形成页面、状态、组件和设计变量清单。
    5. 向用户展示设计计划后再进入设计阶段。

[工作流程]
    [启动阶段]
        第一步：依赖检测
            执行 [依赖检测]

        第二步：加载文档
            读取目标项目需求文档 → 提取所有页面、功能、UI 布局描述、用户流程
            读取目标项目设计简报 → 提取情绪关键词、色彩方向、信息密度、排版方向、交互风格、核心页面视觉备注、状态设计方向

    [规划阶段]
        第一步：提取页面清单
            从 Product Spec 的 UI 布局章节提取所有描述的页面和视图
            从功能需求章节补充可能遗漏的页面
            从用户流程章节确认页面之间的跳转关系

        第二步：确定状态变体
            对每个页面分析需要哪些状态变体
            列出完整的设计交付清单，格式为：页面名 + 需要的状态变体列表

        第三步：提取组件清单
            从页面清单中识别重复出现的 UI 元素
            确定需要创建的可复用组件列表

        第四步：展示设计计划
            向用户展示完整的设计交付清单：
            - 组件数量
            - 页面数量
            - 变体数量
            - 总计设计项数
            用户确认后开始设计

    [设计阶段]
        第一步：获取设计工具指南
            调用设计工具的 get_guidelines 获取设计工具的使用规范和最佳实践

        第二步：设置设计变量
            根据 Design Brief 的色彩、字体、间距方向，通过设计工具 API 设置全局设计变量

        第三步：创建可复用组件
            按组件清单逐个创建
            每个组件创建后截图验证

        第四步：逐页面设计
            按页面清单逐个设计
            每个页面：
            1. 使用可复用组件拼装
            2. 填充真实内容，不使用 Lorem ipsum
            3. 对照 Product Spec 的描述逐项确认布局和内容
            4. 对照 Design Brief 的视觉备注确认风格
            5. 截图验证

        第五步：设计状态变体
            按变体清单逐个设计
            每个变体基于对应页面的默认态修改

    [校验阶段]
        第一步：完整性校验
            对照规划阶段列出的设计交付清单，逐项确认是否已完成：
            - 每个组件是否已创建
            - 每个页面是否已设计
            - 每个状态变体是否已覆盖

        第二步：一致性校验
            检查所有页面之间的视觉一致性：
            - 同一组件在不同页面中外观是否一致
            - 颜色、字号、间距是否全局统一
            - 设计变量是否正确引用

        第三步：对照 Spec 校验
            回读 Product Spec 的功能需求，确认没有功能对应的 UI 被遗漏

        第四步：输出报告
            向用户展示设计完成报告：
            - 已完成的页面和变体列表
            - 设计文件位置
            - 未覆盖的内容及原因（如有）

            引导下一步：
            "设计稿已完成。

             接下来：
             - 默认先调用 /dev-planner 制定开发计划（会参照设计稿）
             - 如果你明确要做 critique / audit / polish / 布局 / 排版 / 打磨，再接 `impeccable` / `audit` / `critique` / `polish` / `layout` / `typeset`
             - 其他 `impeccable` 内建技能只保留手动调用
             - 或直接对话调整设计细节"
