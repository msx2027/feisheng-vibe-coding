[任务]
    在开发前把不可靠事后补救的决定落到目标项目既有真源：范围、模块边界、数据与接口、权限、技术与部署、风险与验证。结论为 `PASS` 后才允许进入 `dev-planner` 与 `dev-builder`。

[依赖检测]
    Skill 启动时第一步自动执行：

    必需：
    - 目标项目根目录和 `.vibe-docs.json`；缺失时先由 `product-spec-builder` 建立项目真源（项目画像 / 宪法设计由控制面的项目宪法路由产出）。
    - 需求文档；需求仍有影响行为、验收、数据、权限、接口或范围的 `未决 / blocked` 时，先回到 `product-spec-builder`。
    - `<skills-root>/tools/architecture-foundation-policy.mjs`；先用其 `requiresArchitectureFoundation` 判定触发，避免把路径词或文件数量误当作高影响变更。

    按需：
    - 已有项目代码、接口契约、项目画像与宪法设计；本轮影响面不清时先用 `rg` 沿 callers/callees 与相关测试缩小范围（有可用的代码图工具时再用）。
    - `docs/项目治理/系统架构.md`；不存在时创建，存在时只做本轮增量更新。

[本包治理继承]
    - 本 Skill 改变架构、契约、数据、权限或部署判断时默认至少 T3；命中 secret、migration、filesystem、shell、network、hook 或无法可靠判断影响面时升级 T3+ hazard mode。
    - 目标项目文档先经 `.vibe-docs.json` 解析；系统架构使用 `systemArchitecture` 角色，文档名为四字中文 `系统架构.md`，不另造平行需求或开发计划。
    - 涉及真实 endpoint、service、public entry、server action、fetch wrapper、IPC / event 通道或 schema 时，先读统一 `接口契约.md`；同一能力只复用或扩展一个契约入口。
    - 需要用户拍板的技术栈、数据归属/迁移、公开接口兼容、权限模型或部署暴露，必须先说明改前后的真实体感、风险和最优建议，取得用户确认后才记为 `PASS`。
    - references 采用 progressive references；正式前端页面仍遵守 UI / token / 组件复用，`.pen` 只使用 Pencil desktop 与 desktop MCP。

[第一性原则]
    **先定不可逆，再写可逆**：先确认架构边界、数据、公开契约、权限与部署，再拆文件和实现细节。

    **地基只管高代价决策**：新项目强制；已有项目只在跨两个以上模块边界，或数据、接口、权限、部署或技术栈发生语义变化时触发。T0/T1 与单模块普通功能不触发。

    **决策与事实分开**：项目画像记录已观察事实；系统架构记录本轮选择、依据、非目标、风险和用户确认。能力未实现可以写“计划中”，但“要不要做”未决时必须 `BLOCKED`。

    **可过期才可信**：需求、接口契约、项目画像、部署或本轮范围变化后，引用的基线 revision 失配即过期；过期结论不得进入开发计划或生产代码。

    **最小足够**：不输出空泛架构报告；只记录会改变目录、依赖方向、数据、公开入口、权限、部署、回滚或验证的决定。

[地基决策维度]
    必须明确：
    - 触发原因、范围与非目标；新项目或高影响变更的判定证据。
    - 模块职责、公共入口、允许依赖与禁止直连关系。
    - 数据归属、生命周期、迁移/兼容策略；无数据时明确“不适用”。
    - 统一接口契约、调用方和兼容策略；无真实接口时明确“不适用”。
    - 权限边界、技术栈与部署暴露；不适用必须给出依据。
    - 最大风险、回滚方式、自动验证与待用户确认项。

[工作流程]
    [第一步：判断是否触发]
        新项目强制进入。已有项目仅在跨两个以上业务/公共模块边界，或数据、接口、权限、部署、技术栈/架构发生语义变化时进入；路径词命中只能提示升级，不能替代影响分析。

        完成条件：明确记录 `触发 / 不触发` 与依据；不触发时直接回到原链路。

    [第二步：建立可审阅基线]
        读取需求、接口契约、项目画像、宪法设计和必要代码证据；在 `系统架构.md` 写本轮范围、非目标、决策、依赖边界、风险、回滚、验证和 sourceRevision。

        完成条件：每个适用维度均为“已确认 / 计划中 / 不适用 / BLOCKED”之一，且没有把未决问题伪装成事实。

    [第三步：请求必要确认]
        只有存在会改变用户选择的架构决策时才提问；一次给出第一性原理下的最优建议、代价与真实体感。用户确认后写入确认时间、决定和基线 revision。

        完成条件：关键决策均有用户确认或有证据证明沿用既有确认；否则为 `BLOCKED`。

    [第四步：输出门禁结论]
        所有必需项已确认或不适用、无 BLOCKED 且基线未过期，输出 `地基 PASS`；否则输出 `地基 BLOCKED`，列出唯一需要用户裁决的事项。

        完成条件：`PASS` 才能交给 `dev-planner` 写计划；`BLOCKED` 或过期时不得进入开发计划或生产代码。

[输出风格]
    - 先说本轮是否触发、能否开工和最大风险；再给最少必要决策。
    - 以“改前/改后真实体感”解释用户要拍板的选择，不堆技术名词。
    - `PASS` 不等于功能完成，只表示可以安全进入计划与编码。

[初始化]
    执行 [第一步：判断是否触发]。
