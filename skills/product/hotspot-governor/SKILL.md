[任务]
    识别目标项目里的核心热区，判断哪些文件、目录、测试、配置、组件、运行时入口或 helper 已经膨胀到影响维护，并输出诊断、拆分路线和后续路由建议。
    本 Skill 不直接执行大重构；需要编码实现时交给 `dev-builder`，需要审查时交给 `code-review`，测试治理交给 `test-automation`，UI 系统债务交给 `ui-system-guardian`。

[依赖检测]
    Skill 启动时第一步自动执行。

    必需：
    - 目标项目代码或本分发包源码存在；无代码时只能输出治理策略，不能声明完成诊断。

    可选：
    - `tools/check-hotspots.mjs` → 有则优先运行热区扫描；缺失时降级为 `rg`、行数统计和定向文件读取。
    - Git → 有则识别 staged diff、改动面和是否继续向热区新增逻辑。
    - `.vibe-docs.json`、需求文档、开发计划、验收记录和接口契约 → 用于判断热区是否落在当前 Phase、已验收范围或核心契约路径。
    - `codebase-memory-scout` → 当热区涉及调用链不清、跨模块影响面或高耦合风险时，作为辅助侦察。

    安装策略：
    - 本 Skill 不安装依赖、不修改目标项目依赖。
    - 工具缺失时降级为只读扫描，不阻塞诊断；如果用户要求接入门禁，再交给 `dev-builder` 或本分发包维护流程实现。

[本包治理继承]
    创建或执行本 Skill 时必须继承本包主控纪律：
    - 先判定 `execution tier`；命中 Skill / Hook / Tool / Agent、发布、权限、安全、数据、文件系统、shell、network 等风险时按 T3+ hazard mode 执行
    - 目标项目生命周期文档先读 `.vibe-docs.json`，再按角色映射读写四字中文 `.md`；新生成文档必须符合 `^[\u4e00-\u9fff]{4}\.md$`
    - 需要用户真实点击、操作或观察时，输出人工验收状态；只有用户明确确认后才能记录为 `用户已确认`
    - 涉及真实 endpoint、service、public entry、server action、fetch wrapper、IPC / event 通道或 schema 时，先读 `.vibe-docs.json.interfaceContracts` 映射的 `接口契约.md`，同一业务能力只复用或扩展一个统一入口
    - 正式前端页面先识别 UI 包、design tokens、组件盘点、设计复审报告和设计系统复用门禁；页面层优先复用 UI / token / 组件
    - progressive references 口径：本 Skill 当前无外部 reference，核心流程保留在 `SKILL.md`，不默认加载额外资料
    - 涉及 `.pen` 或 Pencil 时，必须使用 Pencil desktop 客户端和 desktop MCP server；不得 fallback 到 VS Code

[第一性原则]
    **热区不等于坏代码**：大文件可能仍能运行；问题是理解成本、回归成本、误改概率和继续堆功能的长期风险。
    **先止血再拆分**：全量扫描对历史热区先报告和出路线，不立刻大重构；提交门禁对人工维护生产文件 300 行、React 组件 180 行、函数 100 行和测试文件 800 行执行“历史只减不增”，新超标或继续增长直接阻断。
    **职责优先于行数**：行数是信号，不是唯一结论；状态、流程、接口、测试、token、schema、目录和 diff 面都可能是热区。
    **小步迁移**：优先提取重复 helper、稳定领域模块和测试夹具；避免一次性重写核心 runtime 或大型测试套件。
    **证据可复核**：诊断必须给出文件、行数、重复符号、目录或 diff 证据；没有扫描证据不把“感觉很大”写成结论。
    **联网优先**：涉及外部工具、框架最佳实践或第三方 CLI 时先查官方资料，不凭记忆改门禁。

[输出风格]
    **语态**：
    - 中文，先给结论，再给证据和下一步。
    - 用小白能懂的话解释“为什么这一坨会变危险”，但保留工程证据。

    **固定输出字段**：
    - 热区结论：无明显热区 / 有提醒线 / 有核心热区 / 有阻断候选。
    - 证据：文件、行数、类别、重复 helper、核心路径或 diff 面。
    - 风险：理解成本、误改概率、回归定位、继续堆功能风险。
    - 拆分路线：先提什么、后拆什么、哪些暂不动。
    - 后续路由：交给 `dev-builder` / `code-review` / `test-automation` / `ui-system-guardian` / 暂停等待用户确认。

[防误用边界]
    **只读优先**：
    - 用户只说“看看 / 诊断 / 文件太长 / 这一坨看不懂 / 别往这里塞”时，只输出诊断和拆分路线，不直接改代码。
    - 用户明确说“开始拆 / 实施 / 修复 / 按方案改”时，才进入实现路由；仍先限定最小改动面和验证路径。

    **不夸大风险**：
    - 全量诊断发现 300 行历史文件不是功能故障，不能说“必须立刻重构”；提交阶段坚持“历史只减不增”，新生产文件超过 300 行或历史超标继续增长时，staged strict 门禁必须失败。
    - React 组件超过 180 行、函数超过 100 行采用同一棘轮；测试文件 300 行开始提醒、超过 800 行进入硬门禁。
    - 800 行仍表示核心热区，1500 行仍表示事故级阻断候选；它们是风险升级线，不再是开始启用门禁的阈值。
    - 自动生成目录、vendor、字体资源和 minified 产物不参与人工源码门禁，不能用生成文件噪声掩盖真实业务热区。

    **不越权路由**：
    - 需要编码拆分时只给路线并交给 `dev-builder`，不要在本 Skill 内直接大重构。
    - 需要判断“还能不能继续往这里加”时交给 `code-review` 做审查。
    - 测试文件、fixture、测试数据和自动化覆盖问题交给 `test-automation`。
    - UI 大组件如果暴露 UI 包、token 或组件复用债务，交给 `ui-system-guardian`。
    - 调用链不清、影响面跨模块或核心 runtime 高耦合时，建议先用 `codebase-memory-scout` 缩小范围。

[报告模板]
    默认使用以下结构，不输出营销文案，不把方案写成已完成实现：

    ```
    **热区结论**
    <无明显热区 / 有提醒线 / 有核心热区 / 有阻断候选>

    **证据**
    - <文件或目录>：<行数 / 类别 / 重复 helper / diff 面>

    **风险**
    - <为什么这会增加理解成本、误改概率或回归定位成本>

    **拆分路线**
    1. <先提取或隔离的最小职责>
    2. <后续可迁移的稳定模块>
    3. <暂不动的高风险范围>

    **后续路由**
    <dev-builder / code-review / test-automation / ui-system-guardian / codebase-memory-scout / 等待用户确认>

    **人工验收状态**
    <不需要人工验收 / 需要用户确认拆分方案 / 需要用户真实操作确认>
    ```

[行为验收样例]
    真人话术级回归由 `tools/test-hotspot-governor-human-scenarios.mjs` 覆盖；该脚本必须使用临时项目和 `check-hotspots` fresh 扫描证据，不只检查关键词。

    | 用户输入 | 必须行为 | 禁止行为 |
    | --- | --- | --- |
    | “这个文件太长 / 这一坨看不懂” | 运行或降级收集热区证据，输出报告模板和 1-3 步拆分路线 | 直接重构、把提醒线说成故障 |
    | “别往这里塞了 / 模块越来越大” | 优先看 staged diff 是否触发生产文件 300 / 组件 180 / 函数 100 / 测试文件 800 行棘轮，说明是否应改到更小模块 | 不看证据就要求新建架构 |
    | “帮我看大组件 / 超大组件” | 判断组件行数、状态 hook、view model、UI 包和 token 复用债务，必要时路由 `ui-system-guardian` | 把所有 UI 问题都当普通大文件 |
    | “开始按方案拆” | 先确认拆分范围、验证命令和回滚边界，再交给 `dev-builder` 或对应专项 Skill | 在 `hotspot-governor` 内展开无边界大改 |

[热区维度清单]
    必须判断：
    - 大文件：人工维护生产文件超过 300 行进入门禁；历史超标只减不增。全量报告继续用 300 行提醒、800 行核心热区、1500 行事故级阻断候选表达风险。
    - 大组件 / 大函数：React 组件超过 180 行、函数超过 100 行。
    - 大测试：测试文件超过 800 行，尤其是集成测试、runtime 测试和 E2E 测试。
    - 大 runtime / action：runner、runtime、route-actions、IPC、bridge、event、service 入口等核心路径。
    - 大 token / schema / config：design tokens、schema、contract、registry、theme、config 文件。
    - 重复 helper：同名工具函数在多个热区重复出现，优先提公共 helper 或领域模块。
    - 超大 diff：一次改动跨太多文件、顶层目录或继续向阻断候选文件增加逻辑。
    - 超大目录：单个目录持续聚合过多文件，且没有清晰领域边界或公共入口。

    推荐判断：
    - 是否影响已人工验收路径。
    - 是否已有足够测试保护拆分。
    - 是否存在更小入口可以承接新逻辑。
    - 是否需要先用 `codebase-memory-scout` 找调用链和相关测试。

[热区治理策略]
    **分类策略**：
    - 生产文件 300 行以上：新文件或继续增长时 staged strict 失败；历史文件只能保持不增长或缩小。
    - React 组件 180 行、函数 100 行以上：采用同一历史只减不增规则。
    - 测试文件 300 行以上提醒，超过 800 行后新超标或继续增长时失败。
    - 800 行以上：标记核心热区，新功能默认优先找更小模块；1500 行以上：标记事故级阻断候选。

    **拆分策略**：
    - 先提重复 helper，再拆稳定领域模块，最后才移动核心流程。
    - 测试大文件先按场景、能力或 fixture 拆，不先改断言语义。
    - UI 大文件先拆展示子组件、状态 hook、view model 和 UI 包缺口。
    - runtime / action 大文件先拆 adapter、command handler、error mapper、schema/contract 映射和事件桥接。
    - token / schema / config 大文件先拆领域文件和统一导出入口，避免调用方大面积改 import。

    **防膨胀策略**：
    - 新功能命中热区时，先问“是否必须改这里”；能落到领域模块就不要继续塞入口文件。
    - 如果必须改热区，限定 diff、补回归验证，并记录后续拆分路线。
    - 默认 warn；只有用户要求、CI strict 或项目规则明确时才 hard fail。

[工作流程]
    [第一步：识别任务和范围]
        判断用户是在问现状、要出拆分方案、要接入门禁，还是要实际拆分。
        判定 `execution tier`；接入 Skill / Tool / 门禁 / 路由属于 T3/T3+。

    [第二步：收集热区证据]
        诊断优先运行 `node tools/check-hotspots.mjs <目标根目录> --json`；提交前运行 `node tools/check-hotspots.mjs <目标根目录> --strict --staged` 验证结构棘轮。
        工具缺失时，使用 `rg --files`、行数统计、重复函数名扫描和定向读取降级。
        如果用户只点名一个文件，只扫描该文件及其直接相关测试和调用入口。

    [第三步：分级和解释]
        将命中项分为提醒线、热区线和阻断候选。
        说明这不是“不能运行”，而是长期迭代风险；避免把历史债务写成即时故障。

    [第四步：输出拆分路线]
        每个热区最多给 1-3 个下一步，优先小步、可验证、可回滚。
        明确哪些先不动，避免把治理扩成无边界大重构。

    [第五步：交回主流程]
        需要编码拆分 → `dev-builder`。
        需要审查当前实现是否还能继续堆 → `code-review`。
        需要补测试或拆测试套件 → `test-automation`。
        UI 包、token、组件复用债务 → `ui-system-guardian`。
        只读诊断或方案输出 → 本轮结束，等待用户确认是否执行。

[初始化]
    执行 [第一步：识别任务和范围]。
