# 多会话共享仓库的 Git 纪律（multi-session-git）

> 多个 AI 会话（或人 + AI）同时在同一个工作区/仓库干活时的纪律。
> 来源：目标项目实机教训（2026-09 fs-agent 开发期，多会话同仓反复互相踩脚）。
> 单会话独占仓库时按常规 Git 工作流即可；**一旦可能有第二个会话在同工区工作，本文件全程适用**。

## 1. 开工与写前

- **写文件前先核归属**：`git status` 看当前改动；发现**非己方改动**立即停手，向用户报告请处置，不得顺手改掉、回滚或提交别人的东西；追认后只改自己对该文件的引用。
- **动静先取证归属**：并行会话同工区，任何"文件变了/指纹变了"先取证是谁干的；`--fix` 类命令连带刷新了并行会话的内容指纹时，必须在回执里区分说明。
- **不代提交他人文档**：`--fix` 只刷新工作区指纹，不要把别人改的文档一起提交。

## 2. 暂存与提交

- **禁用 `git add -A` / `git add .`**：多会话同仓只允许逐文件 add。
- **提交必须带路径限定**：`git commit -- <pathspec>`（或 `commit --only -- <pathspec>`），**不信任共享暂存区**——里面可能躺着别人 staged 的东西。
- **多路径 add 后复核提交树**：`git show --stat` / `git ls-tree` 核对这批文件真的都进去了；单条 pathspec 写错会**整批静默不入暂存**（stderr 被吞时更隐蔽）。混入他人文件要照实回执连带归属。
- **HEAD 操作用绝对 SHA**：共享仓库的 HEAD 随时可能被别的会话推进，相对引用（`HEAD~1`）会指错对象。

## 3. 门禁联动（装了热点/结构门禁的项目）

- **`--staged` 读的是暂存区，不是工作树**：修完超限函数/组件后，必须**重新 add 目标文件 → 复检 → 再提交**；只改文件不重新 add，门禁看的还是旧内容。
- **白名单行数预算按门禁 policy 的 LIMITS 算**（如新函数 100 行最紧），不要自设更松的数字；改存量文件前先查剩余余量。
- **门禁被无关文件指纹漂移阻断时**：只修自己范围（`git commit -- <pathspec>` 限定），不要替别人刷指纹。

## 4. 合并与收口

- **合并隔离工区（worktree/分支）前必须 `git merge-tree` 重查**与 main 新提交的同文件交叠；**不得沿用冻结时的零交叠结论**——冻结后 main 可能又动了。有冲突即触发停止条件，停下报告。
- **"全绿"必须落在已提交的树上**：全绿验证可能只是建立在工区未提交文件上；合并/收口前对**已提交树**复跑关键验证，否则绿证据不算数。
- **只读审计窗口要冻结**：审计期间基线会漂移；冻结窗口起止，收尾对最终 HEAD 把结论逐条重验；并发写入期弃用外部工具缓存，改用只读脚本现读。

## 5. 共享元数据

- **提交共享元数据前重取工作区态**：共享的索引/台账/光标文件提交前重新读取当前状态，别用几分钟前的旧快照。
