# beginner-flow-guide route matrix

> 本表只供当前对话已激活的 `vibe-coding-skills` 总入口查找 routeHints；普通自然语言不直接加载本 Skill 或表中具体 Skill。未激活总入口时，路由结果为 `no-skill`；新对话默认关闭，只有先调用总入口后，后续普通自然语言才可路由。
> 自然语言不自动加载具体 Skill；用户尚未在当前对话调用总入口时只保持普通对话或直接动作。

## 1. 决策顺序

1. 先确认用户是否已在当前对话调用 `vibe-coding-skills`，以及总入口是否已明确授权本次路由。
2. 总入口未授权时，保持 `no-skill`；低风险、明确对象的直接动作仍可执行，但不加载具体 Skill。
3. 总入口已授权且快车道条件满足：明确对象（文件 / 路径 / 组件 / 当前选区 / 查询范围 / 非破坏性指定命令）+ 明确动作 + 无风险信号 + 可定向验证 → 直接 T0/T1 闭环，不读完整真源，不跑 health，不进入完整路由链。
4. 总入口已授权且快车道条件不满足时，才把自然中文任务交给 `beginner-flow-guide` 做阶段判断。
5. 如果一句话里同时带多个诉求，先拆主诉和次诉求，不让“顺手一句”冲散主诉。
6. 再判断当前阶段。
7. 阶段判断后判定 `execution tier`。
8. 根据 tier 决定走轻量直接动作还是下游 Skill。
9. 只有高影响歧义时才追问，而且一次最多 1-3 个大白话问题。
10. 主诉闭环后，在同一轮继续接上次诉求，不让用户重复第二遍。

## 1.1 小任务快车道

| 条件 | 判断 |
| --- | --- |
| 明确对象或范围 | 用户点名文件、路径、组件、文案、配置项、当前选区、查询范围、指定单测 / lint / 格式化目标，或当前上下文已经唯一定位 |
| 明确动作 | 改错字、改一句文案、调一个低风险配置、定向查询、单文件格式化、运行一个非破坏性轻量命令，或跑用户指定的局部验证 |
| UI 微调 | 同一组件 / 容器内的大小、位置、间距、颜色、字号、圆角、阴影、透明度等 visual-only 调整，且不改变用户路径、信息层级、响应式结构、全局 token / theme、UI 包契约或真实业务行为 |
| 无风险信号 | 不涉及 bug、安全、权限、数据、接口、auth、permission、security、token、secret、payment、database、migration、data loss、filesystem、shell、network、eval、pre-commit、hook、agent routing、Skill / Hook / Tool 规则、release / deploy / publish、删除 / 重命名 / 迁移行为，且影响面清楚 |
| 可定向验证 | 回读文件、运行 `node --check`、定向脚本、局部 grep 或用户指定命令即可证明 |

### 强信号词模式（命中即T0/T1，无需判断）

| 模式 | 示例 | 判定 |
|---|---|---|
| 「把X改成Y」/「X改为Y」+ 明确文件/组件 | "把Button颜色改成#333" | T1 直接执行 |
| 「错别字/注释/措辞」+ 明确位置 | "改第3行注释措辞" | T0 直接执行 |
| 视觉值替换 + 明确组件 | "字号改成14px" / "间距调成8px" | T1 直接执行 |
| 「看一下[文件名]」 | "帮我看一下 utils.ts" | T0/T1 直接查 |
| 非破坏性命令 | "运行 npm run lint" | T0 直接执行 |

快车道动作：
- 不展示新手导航卡。
- 不跑 `vibe-health-check`。
- 不读取完整 `DOC-MAP.md -> Product-Spec.md -> DEV-PLAN.md`。
- 不进入 `codebase-memory-scout`、`code-review` 或 `doc-sync-guardian`，除非实际改动升级到 T3，或 T2 命中跨模块、公共契约、Phase 完成、用户要求 review / 影响面不清等触发条件。
- 自然语言“错误提示更清楚”“页面卡顿 / 性能”等只作为已激活总入口 routeHints；总入口激活后可指定 `clarify` / `optimize`，也可让自然语言选择对应 Skill。
- 不因“UI / 布局 / 间距 / 对齐 / 位置 / 大小 / polish”等通用视觉词自动进入 `layout` / `polish` / `adapt` / `audit` / `impeccable`；明确完整打磨、响应式结构、审计或系统治理时才升级。
- 最终只报告改动文件和定向验证。

## 2. 显式绕过规则

| 用户信号 | 处理 | 原因 |
| --- | --- | --- |
| 用户通过总入口指定某个 Skill，比如“`vibe-coding-skills bug-fixer`” | 直接执行指定 Skill | 用户已经给了明确入口 |
| 用户先调用总入口，后续只说“页面一直转圈” | 使用已激活总入口的 routeHints 进入 `bug-fixer` | 当前对话已获得用户授权 |
| 明确问“有哪些 Skill”“怎么手动触发” | 先回答入口，再补手动调用方式 | 这是在问入口本身 |

## 2.1 外部强规划 Skill 边界

`superpowers:brainstorming` 是外部强规划 Skill，只在用户显式点名、明确要求头脑风暴 / 多方案探索，或需求尚未成形且确实需要先构思时使用。已批准计划、继续执行、明确 bug、明确测试、文档同步、发布、明确文件修改和 T0/T1 快车道任务不得被它拦截。

| 用户常见说法 | 默认下一步 | 不该怎么走 |
| --- | --- | --- |
| 用 superpowers:brainstorming 帮我想方案 | `superpowers:brainstorming` | 不绕过用户显式点名 |
| 按这个计划执行修复 | `dev-builder` / 当前计划执行链 | 不重新进入 `superpowers:brainstorming` |
| 这个报错了 → 总入口指定 `bug-fixer` | `bug-fixer` | 不先做头脑风暴，也不因自然话单独加载 |
| 补 Playwright 测试 → 总入口指定 `test-automation` | `test-automation` | 不当成普通功能构思，也不因自然话单独加载 |
| 改 README 这一句 | T0/T1 快车道 | 不启动强规划流程 |
| 把这个按钮往上移 2px / 这个卡片间距小一点 | T1 UI 微调快车道 | 不启动设计质量层 |

| 现在该怎么分阶段做 / 先做什么 | 计划 | `dev-planner` | 需求已清楚但没计划 | 先补计划；T2/T3 首个 RED 前完成预实现一致性分析 |

| 帮我 review / 检查有没有漏 / 看质量 / 帮我看看写得有没有问题、有没有坑 | 审查 | `code-review` | 有明确改动、交付物或最近实现 | 没明确对象先看现状；小白说“有没有坑 / 写得对不对”等价于代码审查 |

| 帮我同步文档 / README 对齐一下 | 文档同步 | `doc-sync-guardian` | 行为改了但文档没跟上 | 先核对文档现状 |
| 文档越来越大 / 文档太多 / context 太慢 / 需求文档变臃肿 / 开发计划太长 | 文档膨胀治理 | `doc-sync-guardian` 审计模式 | 用自然话描述问题 | 说明目标项目生命周期文档超合理大小时，应触发审计而非继续加载 |
| 准备发布 / 部署 / 上线 / 我做完了怎么让别人也能打开用 | 发布 | `release-builder` | 已到交付前 | 前置没齐先指出缺口；小白说“让别人也能打开用”是发布 / 上线，走 `release-builder` 并区分自动化验证与待用户验收 |

## 4. 直接动作映射

| 用户常见说法 | 当前判断 | 马上动作 | 什么情况下优先这么做 |
| --- | --- | --- | --- |
| 你先看看现在做到哪了 | 接手现状 | 先读 `.vibe-docs.json`，经 resolver 取得 `documentIndex/currentExecution`；用 `rg` 定位光标稳定字段后只读命中附近内容 | 用户先要知道当前状态，不先全文读取开发计划 |
| 先帮我看看文档 / 代码现状 | 现状扫描 | 先读相关文档或代码 | 还不该直接跳下游 Skill |
| 先跑一下验证 | 常见检查 | 先跑已有检查或验证 | 用户明确要求跑某个验证或当前最需要的是证据 |
| 我现在该干嘛 / 我不会走流程 / 你先帮我看看 | 新手迷茫入口 | 先显示新手导航卡，再做 micro preflight：项目标记、manifest、package scripts 和必要文件存在性 | 当前目录像项目仓库，且用户没有给出更明确的需求 / bug / 发布目标 |
| 这个项目有没有问题 / 能不能跑 / 体检 | 新手体检入口 | 先显示新手导航卡，再运行对应 package / target quick health | 用户明确要求检查项目健康、能否运行或质量问题 |
| 先看影响面 / 先查调用链 / 先用代码地图定位 | 代码图侦察 | 先用 `codebase-memory-scout` 缩小候选文件、函数、调用链和测试 | 用户明确点名，或 T2/T3 且跨模块、调用链不清、入口不明、影响面不明 |
| 这个文件太长 / 这一坨看不懂 / 别往这里继续塞 | 核心热区治理 | 走 `hotspot-governor` 输出热区诊断和拆分路线 | 覆盖大文件、大测试、runtime/action、token/schema/config、超大 diff 和重复 helper |
| 这个第三方规则现在怎么用 / 官方怎么说 | 先查资料 | 先联网查资料 | 涉及外部知识或最新信息 |
| 我不会走流程 | 接管信号 | 有目标就按目标接管；没目标但像项目仓库时先显示新手导航卡并做 micro preflight / 状态扫描 | “我不会走流程”不是独立阶段 |
| 把 PRD / 需求文档转成测试用例体系 | 测试设计 | 走 `requirements-test-designer` | 先产出需求追溯、正反边界等生产级用例和自动化候选；只有用户要写测试代码时才切 `test-automation` |
| 帮我加自动化测试 / 补 E2E / 跑回归 | 自动化测试 | 走 `test-automation` | 明确是测试自动化时才切 |
| 帮我做自动化 / 定时任务 / 周期提醒 / 自动化办公 | 自动化任务 | 使用当前运行时的自动化 / 提醒工具或宿主能力处理；无可用工具时说明缺口并给手动替代，不走 `test-automation` | 没有测试、E2E、回归、覆盖率等信号时不要误路由到测试 Skill |
| 别人写了一半 / AI 写乱了 / 项目越来越乱 | 半路接管 | 先收集现状证据、真实启动状态、已有 owner、接管风险和第一个安全任务 | 半路接管不按空项目重建；先只读审计，再决定是否写文档或改代码 |
| 本地打不开 / 怎么启动 / 端口被占用 / 环境变量怎么填 | 环境启动 | 先读取 package scripts、README、环境示例和端口配置，运行最小可运行性验证 | 优先给 fresh 证据；不让用户手输大段命令 |
| 我怎么确认 / 能不能给用户用 / 上线前检查 | 验收上线 | 走 `release-builder` 或验收链路，区分自动化验证、待用户验收和发布前 smoke | 自动化通过不等于用户已确认 |
| 会不会泄露 / env 能不能提交 / 内部资料不能推 | 安全隐私 | 升级 T3+ `hazard mode`，检查 secret、token、权限、隐私文件和发布风险 | 不走小任务快车道，不自动删除文件，先给风险和验证证据 |
| 改 README 一句 / 按钮颜色 / 组件间距 / 只查这个文件 | 小改快车道 | 明确对象 + 明确动作 + 低风险时走 T0/T1；按钮颜色和组件间距属于 UI 微调快车道 | 不进入 `impeccable` 或完整设计质量层 |

## 5. 执行强度分级

| Tier | 场景 | 默认动作 | 升级条件 |
| --- | --- | --- | --- |
| T0 `trivial` | 低风险错字、注释、纯说明文字 | 直接动作 + diff 摘要 | 涉及命令、规则、代码语义、安全或工作流时升级 |
| T1 `light` | 小范围 UI copy、样式、同一组件 / 容器内 UI 微调、低风险配置 | 微计划 + 定向验证 | 影响状态逻辑、数据流、路由、接口、响应式结构、全局 token / theme 或 UI 包契约时升级 |
| T2 `standard` | 普通功能、组件、状态逻辑 | 进入现有专业 Skill 主链路 | 涉及 bug、安全、数据、发布或工作流规则时升级 |
| T3 `strict` | bug、安全、权限、数据、发布、Skill / Hook / Tool / Agent 路由变更 | 严格根因、回归、review、doc-sync | 不降级；只能证明是 typo / copy 后另行重判 |

混合批次按最高 tier 执行；无法可靠分类时升到 T2/T3。

## 6. 复合意图闭环

| 用户原话 | 主诉怎么判 | 次诉求怎么保留 | 默认闭环 |
| --- | --- | --- | --- |
| 修完顺手检查有没有漏 | 主诉 = 修复 | 次诉求 = 审查 | 先 `bug-fixer`，拿到 fresh 证据后自动续到 `code-review` |
| 这个 bug 修一下，再帮我看看有没有漏 | 主诉 = 修复 | 次诉求 = 审查 | 修完继续 `code-review`，不默认停在 `commit` |
| 继续下一步，但这里有个 bug | 先恢复当前任务，再看 bug 是否阻塞主线 | 次诉求 = 回到当前任务继续 | bug 是阻塞点就先修，修完回原任务 |
| 帮我看看有没有漏 | 有明确改动时，主诉 = 审查 | 无 | 直接 `code-review`；没对象就先看现状 |
| 我不会走流程，但想修 bug / 想继续做 / 想加功能 | “我不会走流程”只是接管信号 | 无 | 按真正目标路由，不先列 Skill 名 |

## 7. 高影响歧义才追问

只有这些会明显改变后续动作的情况，才允许追问，而且一次最多 1-3 个大白话问题。

| 模糊场景 | 为什么要问 | 推荐问法 |
| --- | --- | --- |
| “改排序”“排序不对” | 可能是新需求，也可能是 bug | 这是原来能用现在坏了，还是你想改成新的规则？ |
| “继续下一步，但这里有个 bug” | 会影响先修 bug 还是先恢复主线 | 这个 bug 是当前这条主线卡住的点，还是另一个顺手想修的问题？ |
| “帮我看看有没有漏” | 会影响走 `code-review` 还是先做现状扫描 | 你是想让我查这次改动有没有漏，还是看看流程下一步有没有漏？ |
| “我不会走流程” | 只有接管信号，没有任务目标 | 你现在更想加功能、修 bug，还是先让我看下一步？ |

## 7.1 需求说不清（意图还没成形）

这一节和第 7 节不同：第 7 节是“用户知道要啥、只是一句话有歧义”；这一节是**用户自己都还没想清楚要啥**，只有情绪或模糊不满。信号包括：只说“感觉怪怪的 / 不太对 / 不好用”这类情绪却没有对象；把判断丢回来（“你看着办 / 你觉得呢”）；直接说“我也不知道咋说 / 说不清”；或愿望大到没法下手（“做个像抖音那样的”）。

当前对话已激活总入口并把这类**需求还没成形**的输入交给本 Skill 时，进入澄清模式，按下面四条挖；未激活总入口时保持 `no-skill`，不要硬猜也不要甩选项：

| 规矩 | 做法 | 为什么 |
| --- | --- | --- |
| 意图不清，禁止直接开干 | 不动手改代码，也不走 T0/T1 快车道（快车道前提是对象和动作都清楚，这里正相反） | 越能干活越怕猜错，猜错的返工代价最大 |
| 一次只问一个 | 一轮只抛一个大白话问题，不摆 A/B/C/D 表单 | 用户本来就懵，再糊一脸选项会直接放弃 |
| 先给猜测让你点头 | 用“你是说 X，还是 Y？”给具体猜测让用户点头摇头；必要时请他“截个图 / 说说你点了啥然后咋了”，用他的世界不用行话 | 反应比表达容易，不让用户从零组织语言 |
| 挖到能下手就停 | 挖到能一句话说清“给谁用、解决啥、做完啥样算成”就停，转对应主 Skill，不追问到细枝末节，也不中途擅自升级成大改 | 够用就停，追问过细对小白也是负担 |

| 用户说法 | 当前判断 | 马上动作 |
| --- | --- | --- |
| 这个感觉怪怪的 / 不太对 | 需求还没成形 | 先给猜测让你点头，禁止直接开干：例如“你是说打开后不知道先看哪儿，还是点了半天找不到想要的？” |
| 你看着办吧 / 你觉得呢 | 需求还没成形 | 一次只问一个大白话问题把方向定下来，不代替用户拍板方向 |
| 我也不知道咋说 / 反正就是不好用 | 说不清 | 先问再动：请他说“在哪一步、点了啥、期望啥”，或截个图，定位到具体对象再路由 |

## 7.2 排版乱这类天生歧义

| 用户说法 | 为什么要先反问 | 推荐问法 |
| --- | --- | --- |
| 排版乱了 / 错位了 | 排版乱可能是代码坏了（bug），也可能是设计没做好；两条路一个走 `bug-fixer` 一个走设计链 | 先反问是坏了还是想改：这是原来正常现在突然乱了，还是一直这样你想让它更整齐？ |

## 8. 恢复优先规则

| 场景 | 默认处理 |
| --- | --- |
| 用户说”继续””下一步””接着做” | **轻量探针优先**：先读 `.vibe-docs.json`，运行 `resolve-target-doc-context` 请求 `documentIndex,currentExecution`；再用 `rg -n --max-count 3 "^(## 当前任务|- 状态：|- 下一步：)" <执行光标>` 定位并小块读取。光标明确 → 直接执行；不足时只向 resolver 增加当前任务所需显式 role，禁止按固定顺序全文恢复需求和计划；`never` 不得绕过 |
| 当前已有 `doing` | 先恢复这条线，不先新开流程 |
| 当前已有 `blocked` | 先说清阻塞点，再做最小解堵动作 |
| “继续下一步，但这里有个 bug” | 先恢复，再判断 bug 是不是当前主线阻塞点 |

## 9. 页面设计默认主链

| 用户常见说法 | 默认下一步 | 不该怎么走 |
| --- | --- | --- |
| 前端页面设计 / 页面风格 / 页面方案 | `design-brief-builder` 提示 | 必须先激活总入口；激活后可由自然语言路由或指定 Skill ID |
| 配色 / 字体 / tokens / design system | 对应 routeHints | 不直接启动 Skill；必须先激活总入口，激活后可由自然语言路由或指定 ID |
| 初始化组件库 / 补 token / 补组件 / 治理 UI 债务 / 样式不统一 / check-ui-reuse 报错 | `ui-system-guardian` 提示 | 必须先激活总入口；激活后可由自然语言路由或指定 Skill ID |
| critique / audit / polish / 布局 / 排版 | 对应 routeHints | 不直接启动 Skill；明确对象和动作的 UI 微调仍可直接走 T1 快车道 |
| 移动端适配 / 响应式 / 在手机上打开全是乱的 | `adapt` 提示 | 必须先由总入口指定 ID |
| 微交互 / 过渡 / motion | `animate` 提示 | 必须先由总入口指定 ID |
| 惊喜感 / 更有趣 / 人格化体验 | `delight` 提示 | 必须先由总入口指定 ID |
| 空状态 / 边界情况 / 生产可用 | `harden` 提示 | 必须先由总入口指定 ID |
| 页面卡顿 / 性能 / 点一下要等好久越来越卡 | `optimize` 提示 | 必须先由总入口指定 ID |
| 总入口指定 `shape` / 用总入口路由 shape | `shape` | 普通自然语言不直接启动；普通页面设计规划仍走 `design-brief-builder` |

## 9.1 设计质量层边界

明确对象和动作的 UI 微调快车道不进入设计质量层；只有完整设计质量、响应式结构、系统治理、审计或用户显式点名时才进入。

| 用户语义 | 默认下一步 | 边界 |
| --- | --- | --- |
| 代码 / Spec / 实现完整性、查漏补缺 | `code-review` | 关注 Spec / diff / 实现完整性，不替代技术审计 |
| 可访问性 / 性能 / 主题 / 响应式 / 反模式评分 | `audit` 或 `optimize` | 关注 accessibility / performance / theming / responsive / anti-pattern |
| 设计判断、视觉层级、信息架构、UX 反馈 | `critique` | 关注设计判断，不替代代码完整性审查 |
| 配色、字体、tokens、design system、资料或规则增强 | `ui-ux-pro-max` / `design-system` / `ui-styling` / `brand` | 关注资料 / 规则增强 |
| 微交互、过渡、motion | `animate` | 关注 motion / transition / micro-interaction |
| 惊喜感、更有趣、人格化体验 | `delight` | 关注情绪 / 惊喜 / 人格化体验 |
| 交付前一致性、细节 QA、finishing touches | `polish` | 关注交付前一致性 |

## 10. 兜底规则

| 情况 | 兜底做法 |
| --- | --- |
| 没有目标项目需求文档，但用户想直接开做 | 明确说现在还在需求阶段，先补需求 |
| 有目标项目需求文档，没有目标项目开发计划，但用户想继续开发 | 先补计划，再开做 |
| 请求只适合先看现状 | 先做现状扫描，不强行下钻 Skill |
| 请求超出当前聊天内自动接管边界 | 直接说明不在本 Skill 范围，再给最接近的安全下一步 |
| 看不清属于哪个阶段，但能先拿证据 | 先做“看项目状态”或“看文档代码现状” |

## 11. 新手自动预检 / 体检规则

| 环境信号 | 默认动作 |
| --- | --- |
| 用户只是说“我不会走流程 / 我现在该干嘛 / 先帮我看看”，当前目录存在 `.vibe-docs.json` 或 `package.json`，且有 `tools/vibe-health-check.mjs` | 运行 target micro preflight：`node tools/vibe-health-check.mjs . --profile target --level micro` |
| 用户只是说“我不会走流程 / 我现在该干嘛 / 先帮我看看”，当前目录存在 `AGENTS.md`、`skills/`、`tools/vibe-health-check.mjs` | 运行 package micro preflight：`node tools/vibe-health-check.mjs . --profile package --level micro` |
| 用户明确说“这个项目有没有问题 / 能不能跑 / 体检”，当前目录存在 `.vibe-docs.json` 或 `package.json`，且有 `tools/vibe-health-check.mjs` | 运行 target health：`node tools/vibe-health-check.mjs . --profile target --level quick` |
| 用户明确说“这个项目有没有问题 / 能不能跑 / 体检”，当前目录存在 `AGENTS.md`、`skills/`、`tools/vibe-health-check.mjs` | 运行 package health：`node tools/vibe-health-check.mjs . --profile package --level quick` |
| 当前目录存在 `package.json`，但没有 health 工具 | 读取 package scripts，优先找 build / test / smoke / check 类脚本，做状态扫描 |
| 当前目录存在 `.vibe-docs.json` | 先解析 schema v2/loadPolicy，经 resolver 读取 `文档索引.md` 与当前光标 selector；README、需求和计划只在 resolver 显式返回时读取 |
| 当前目录存在 `.claude/.needs-doc-sync` 文件 | 在 micro preflight 结果中补一条提醒："⚠️ 检测到未完成的文档同步标记（.needs-doc-sync），建议说"帮我同步文档"处理" |
| 找不到项目特征 | 只问 1 个大白话问题：你现在更想加功能、修 bug，还是先让我看下一步？ |

新手自动预检或体检前必须先输出新手导航卡；卡片必须用真实 Markdown 渲染 `# 馬师兄`、`## 新手接管模式` 和粗体“馬师兄接管中。”，禁止包进代码块；输出后继续执行，不把命令交给用户手动输入。

## 12. 固定输出模板

```text
当前判断：一句话，先说现在属于什么阶段，或为什么先做直接动作。
马上动作：一句话，先说现在立刻要做什么。
继续接管：一句话，说明我会直接往下做，不让用户自己选流程或输入命令。
```
