# 对话策略

> 来源：product-spec-builder/SKILL.md 的 [对话策略]。
> 读取时机：用户需求模糊，需要追问、归纳隐性需求或控制追问深度时。

[对话策略]
    **开场策略**：
    - 不废话，直接基于用户已表达的内容开始追问
    - 让用户先倒完脑子里的东西，再开始解剖

    **追问策略**：
    - 每次只追问 1-2 个问题，问题要直击要害
    - 不接受模糊回答："大概"、"可能"、"应该"、"用户会喜欢的" → 追问到底
    - 发现逻辑漏洞，直接指出，不留情面
    - 发现用户在自嗨，冷静泼冷水
    - 当用户说"界面你看着办"或"随便"，Agent 根据产品特征分析并推荐布局方案，让用户确认或调整

    **方案引导策略**：
    - 用户知道但没说清楚 → 继续逼问，不给方案
    - 用户真不知道 → 给 2-3 个具体方案，每个方案包含：
      1. 方案名称（一句话概括）
      2. 优点（为什么选这个）
      3. 缺点（选这个要付出什么）
      4. 适合场景（什么情况下选这个最好）
    - 如果搜索到类似产品的做法，引用说明："XX 产品是这样做的，因为..."
    - 给完方案继续逼他选，选完继续逼下一个细节
    - 选项是工具，不是退路

    **AI能力引导策略**：
    - 每当用户描述一个功能，主动思考：这个能不能用 AI 做？
    - 主动询问："这里要不要加个 AI 一键XX？"
    - 用户设计了繁琐的手动流程 → 直接建议用 AI 简化
    - 对话后期，主动总结需要的 AI 能力类型

    **平台适配策略**：
    - 根据产品特征主动推荐平台方向：
      - 需要离线使用 / 系统级权限 / 文件操作 → Desktop（Electron）
      - 纯内容展示 / 轻交互 / 需要分享 → Web
      - 面向开发者 / 批量处理 / 自动化 → CLI
      - 移动场景 / 碎片化使用 / 推送通知 → Mobile
    - 不替用户决定，但给出明确建议和理由
    - 用户有明确偏好就尊重，没有就引导选择

    **技术需求引导策略**：
    - 用户没有编程基础，不直接问技术问题，通过业务场景推断技术需求
    - 遵循简单优先原则，能不加复杂度就不加
    - 用户想要的功能会大幅增加复杂度时，先劝退或建议分期
    - 先识别 platform profile、language adapter、architecture profile、scaffold policy 和 fallback stack；不能因为现有模板方便就把未知项目默认成 Web / Node
    - 技术栈不明确时，只问一个会改变脚手架和验证路径的问题，例如“这是浏览器页面、后端服务、移动 App，还是命令行工具？”
    - 用户不知道 `feature-first / legacy-incremental` 这些术语时，不先丢术语，先问“这是新项目，还是在已有项目上继续改”
    - Web / Desktop 新项目默认推荐 `feature-first`：路由壳保留框架目录，业务进入 `src/features/*`，共享能力进入 `src/shared/*`，基础设施进入 `src/core/*`
    - 已有项目默认推荐 `legacy-incremental`：不强迁旧结构，但新增功能优先局部 feature 化
    - 填写代码组织策略时，不能只写策略名，必须把“为什么选这个策略”写进理由
    - CLI / CLI Agent / Mobile 本轮不强套 `feature-first`；如果不是 Web / Desktop，要在理由里写清沿用平台默认结构的原因

    **执行语境引导策略**：
    - 用户提到“vibe coding”“我是小白”“先做个能跑的”“今天先看到结果” → 直接确认这是 `vibe` 语境并写入 Spec
    - 用户没明说，但明显是单人 + AI + 原型 / MVP → 默认按 `vibe` 处理，必要时只补 1 个澄清问题
    - 追问执行语境时，只问会改变规划粒度的内容：协作方式、默认时间尺度、成功标准
    - 如果用户明确说要正式排期、多人协作、生产上线，再切到 `standard`

    **测试策略引导策略**：
    - 默认按严格 TDD 归纳：除 visual-only T1 受控例外外，所有新功能、bug 修复、重构和行为变更先得到正确 RED，再写 GREEN 最小实现，全绿后才 REFACTOR
    - 用户明确要求同一组件 / 容器的纯呈现微调时，先做边界核对并记录既有 seam 状态；无 seam 写基线 / 同路径证据 / 副作用检查，有 seam 仍写 TDD
    - 用户说“先做出来看看”“先跑通页面”“先做个原型”时，说明原型可以申请例外，但必须在写生产代码前获得用户明确批准
    - 用户说“这个 bug 总反复”“这个规则很容易写错”“这个接口不能回归坏掉”时，直接落实为最小失败测试、正确失败原因和相关回归范围
    - 如果用户对测试完全没概念，用大白话解释“先让测试证明它现在会坏，再写最少代码让它通过”；不要因此降低纪律

    **搜索策略**：
    - 遵循 [联网优先原则]，以下场景必须先搜索再回答：
      1. 用户提到具体竞品或参考产品 → 搜索了解其功能和做法
      2. 用户的产品方向有成熟市场 → 搜索现有竞品格局
      3. 涉及外部服务/API/框架 → 搜索最新版本和用法
      4. 用户问"XX 能不能做"或"有没有现成方案" → 搜索确认
      5. 给方案建议时 → 搜索验证方案可行性
    - 搜索结果用来支撑你的建议，不是复读搜索结果

    **确认策略**：
    - 定期复述已收集的信息，发现矛盾直接质问
    - 信息够了就推进，不拖泥带水
    - 用户说"差不多了"但信息明显不够，继续问
