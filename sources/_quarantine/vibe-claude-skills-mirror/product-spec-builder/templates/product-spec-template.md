# Product Spec 输出模板

本模板用于生成结构完整的 Product Spec 文档。生成时按照此结构填充内容。

---

## 模板结构

**文件命名**：需求文档.md
**文档映射**：`.vibe-docs.json` 中 `productSpec = "需求文档.md"`
**人工验收映射**：`.vibe-docs.json` 中 `manualAcceptance = "验收记录.md"`
**接口契约映射**：`.vibe-docs.json` 中 `interfaceContracts = "接口契约.md"`

命名规则：
- 新目标项目生命周期 `.md` 文档文件名必须是正好 4 个汉字
- 新项目需求文档默认路径固定为 `docs/需求文档.md`
- 不允许在新目标项目里生成 `Product-Spec.md`

## 术语与命名规范

| 对象ID | 类别 | 统一口径 | 禁用别名 | 代码命名映射 | 适用范围 | 状态 | 说明 |
|------|------|----------|----------|--------------|----------|------|------|
| <stable-kebab-case-id> | <核心对象 / 页面 / 状态 / 动作 / 模块 / 公开文案> | <对外唯一主名> | <不再继续混用的别名；可留空> | <canonical snake_case base name> | <影响到哪些页面 / 模块 / 文档> | <active / deprecated> | <边界和解释> |

填写规则：
- 表头固定为：`对象ID | 类别 | 统一口径 | 禁用别名 | 代码命名映射 | 适用范围 | 状态 | 说明`，不要改列名、不要删列
- `对象ID` 必须是稳定的 `kebab-case`，全表唯一；一旦创建，不因中文主名变化而改名
- `类别` 只允许：`核心对象 / 页面 / 状态 / 动作 / 模块 / 公开文案`
- 一个核心对象只保留一个主名，不要同时出现 2-3 个近义词
- `禁用别名` 允许留空；非空时把所有不再继续混用的叫法都写进来，后续检查器会按 `、，；;/` 自动拆分
- `代码命名映射` 只写 canonical `snake_case` 基名；后续实现和检查器会据此派生 `camelCase / PascalCase / kebab-case / UPPER_SNAKE_CASE`
- `状态` 只允许 `active / deprecated`
- 用户文案、文档术语和代码标识要能建立一对一映射
- 如果用户是小白、说不清术语，先根据显性需求和隐性需求帮他定名，再写进这一节
- 新增主名、替换旧名或收敛别名时，必须更新这一节，不能只在聊天里说

## 技术方向

| 维度 | 选择 | 理由 |
|------|------|------|
| 产品类型 | <Web / Desktop / CLI / Mobile / Backend / Library / Agent> | <为什么选这个平台> |
| 推荐技术栈 | <如 Next.js + TypeScript + Tailwind> | <为什么选这套技术> |
| Platform Profile | <Web / Desktop / CLI / Mobile / Backend / Library / Agent> | <为什么这是当前产品形态> |
| Language Adapter | <TypeScript / Python / Go / Rust / Java / C# / PHP / Swift / Dart / 既有项目语言> | <为什么用这个语言和运行时> |
| Architecture Profile | <frontend / fullstack / service / worker / library / desktop-shell / mobile-app / cli-tool / cli-agent> | <架构形态和部署方式如何影响目录、测试和接口> |
| Scaffold Policy | <template / platform-default / existing-incremental / ask-once> | <是否使用内置模板；如果不使用，沿用哪个平台约定> |
| Fallback Stack | <不适用 / 已确认 / 需确认> | <技术栈缺失时问过什么关键问题，或继承了什么现有工程痕迹> |
| 代码组织策略 | <feature-first / legacy-incremental / 平台默认结构> | <为什么按这种方式组织代码；不能只写策略名> |
| 数据存储 | <本地 / 云端 / 混合> | <基于产品需求的判断> |
| 部署方式 | <静态托管 / 服务器 / 桌面安装包 / App Store / 包仓库 / 内网运行> | <根据产品类型> |

填写规则：
- 新 Web / Desktop 项目默认写 `feature-first`，理由里要明确：路由壳留在框架目录，业务进入 `src/features/*`，共享能力进入 `src/shared/*`，基础设施进入 `src/core/*`
- 已有项目迭代默认写 `legacy-incremental`，理由里要明确：不强改旧结构，但新增业务优先局部收进 feature 模块
- 如果产品类型不是 Web / Desktop，可以写 `平台默认结构`，但理由里要解释为什么不套用本轮模块化策略
- 只有明确匹配 Web / Desktop / Node CLI 时，`Scaffold Policy` 才能写 `template`；Backend、Library、Mobile、非 Node CLI 默认写 `platform-default` 或 `existing-incremental`
- 技术栈不明确时不要把推荐技术栈写成 Next / React / Node fallback；先问清平台、语言或部署目标

## 接口契约治理

| 项目 | 设定 | 说明 |
|------|------|------|
| 契约台账 | `接口契约.md` | 通过 `.vibe-docs.json.interfaceContracts` 映射 |
| 核心原则 | 同一业务能力一个统一契约入口 | 已有 endpoint / service / public entry / schema / event 能覆盖时，复用或扩展，不另造平行接口 |
| 新增入口条件 | <明确能力边界差异 + 调用方影响 + 测试证据> | 不能说明和旧入口差异时不得新增 |
| 门禁 | `check-api-contracts.mjs` | 新增 API route、service/public entry、fetch 调用、server action、IPC / event 通道或 schema 后运行 |

填写规则：
- 如果第一版没有真实接口，写明“暂无业务接口”，但仍生成 `接口契约.md`。
- 如果需求里出现“提交、保存、生成、删除、同步、支付、授权、调用外部 API”等真实动作，必须登记对应业务能力。
- 每个能力后续在 `接口契约.md` 固定表中登记：`能力ID | 统一能力 | 入口类型 | 契约入口 | 调用方 | 状态 | 说明`。
- `入口类型` 只允许 `endpoint / service / publicEntry / schema / event / none`；server action 通常登记为 `publicEntry` 或 `service`，fetch wrapper 登记为 `service`，IPC / event 通道登记为 `event`。

## 测试与验证策略

| 项目 | 设定 | 说明 |
|------|------|------|
| 默认策略 | 严格 TDD | 除 visual-only T1 受控例外外，所有新功能、bug 修复、重构和行为变更强制 RED-GREEN-REFACTOR |
| RED | <最小失败测试 / 运行命令 / 预期失败原因> | 没有先失败且失败原因正确的测试，不得写生产代码 |
| GREEN | <最小生产代码边界 / 测试与回归命令> | 只写让当前测试通过的最小实现，相关测试全绿后才算 GREEN |
| REFACTOR | <允许的整理范围 / 保持全绿命令> | 只在全绿后整理，不新增行为 |
| 例外审批 | <原型 / 生成代码 / 配置文件，或不适用> | 必须在写生产代码前获得用户明确批准，并记录替代验证、风险和恢复方案；无法自动化不属于例外类型 |
| 受控 T1 | visual-only T1 受控例外 | 边界核对通过且没有既有测试 / visual regression seam 时，记录 seam 结论、改前基线、改后同路径定向视觉证据与副作用检查；已有 seam 或越界时恢复严格 TDD |
| 分支化完成证据 | 严格 TDD Task：<RED 失败 + GREEN 通过 + 必要回归>；受控 T1 Task：<边界 + seam + 基线 + 同路径证据 + 副作用> | 编译、启动、smoke 和人工验收只能补充，不能替代对应分支的主证据 |
| 人工验收 | <真实点击 / 操作 / 观察确认> | <UI、设计、CLI 人机流程、权限、端到端链路、发布安装等自动化无法完全证明时必须提醒用户验收> |
| 人工验收记录 | <验收记录.md> | <用户明确确认后记录；后续改动命中已确认范围时先做影响分析和自动化回归> |

## 完整示例

以下是一个「剧本分镜生成器」的 Product Spec 示例，供参考：

```markdown
## 产品概述

这是一个帮助漫画作者、短视频创作者、动画团队将剧本快速转化为分镜图的工具。

**目标用户**：有剧本但缺乏绘画能力、或者想快速出分镜草稿的创作者。他们可能是独立漫画作者、短视频博主、动画工作室的前期策划人员，共同的痛点是「脑子里有画面，但画不出来或画太慢」。

**核心价值**：用户只需输入剧本文本、上传角色和场景参考图、选择画风，AI 就会自动分析剧本结构，生成保持视觉一致性的分镜图，将原本需要数小时的分镜绘制工作缩短到几分钟。

## 应用场景

- **漫画创作**：独立漫画作者小王有一个 20 页的剧本，需要先出分镜草稿再精修。他把剧本贴进来，上传主角的参考图，10 分钟就拿到了全部分镜草稿，可以直接在这个基础上精修。

- **短视频策划**：短视频博主小李要拍一个 3 分钟的剧情短片，需要给摄影师看分镜。她把脚本输入，选择「写实」风格，生成的分镜图直接可以当拍摄参考。

- **动画前期**：动画工作室要向客户提案，需要快速出一版分镜来展示剧本节奏。策划人员用这个工具 30 分钟出了 50 张分镜图，当天就能开提案会。

- **小说可视化**：网文作者想给自己的小说做宣传图，把关键场景描述输入，生成的分镜图可以直接用于社交媒体宣传。

- **教学演示**：小学语文老师想把一篇课文变成连环画给学生看，把课文内容输入，选择「动漫」风格，生成的图片可以直接做成 PPT。

## 执行语境

| 项目 | 设定 | 说明 |
|------|------|------|
| 交付模式 | vibe | 单人 + AI 的原型开发，优先先跑通 |
| 用户类型 | 创作者 / 非专业开发者 | 需要低门槛推进产品 |
| 协作方式 | 单人 + AI | 不默认假设多人团队 |
| 默认时间尺度 | 当前 session / 今天 | 大任务拆成多轮，不先换算成几周 |
| 成功标准 | 先生成第一版可用分镜 | 后续再补历史、导出、工程化 |
| 回复约束 | 优先说“这轮先做什么、做完能看到什么” | 不默认说“Sprint 1 / 2 周计划” |

## 功能需求

**核心功能**
- 剧本输入与分析：用户输入剧本文本 → 点击「生成分镜」→ AI 自动识别角色、场景和情节节拍，将剧本拆分为多页分镜
- 角色设定：用户添加角色卡片（名称 + 外观描述 + 参考图）→ 系统建立角色视觉档案，后续生成时保持外观一致
- 场景设定：用户添加场景卡片（名称 + 氛围描述 + 参考图）→ 系统建立场景视觉档案（可选，不设定则由 AI 根据剧本生成）
- 画风选择：用户从下拉框选择画风（漫画/动漫/写实/赛博朋克/水墨）→ 生成的分镜图采用对应视觉风格
- 分镜生成：用户点击「生成分镜」→ AI 生成当前页 9 张分镜图（3x3 九宫格）→ 展示在右侧输出区
- 连续生成：用户点击「继续生成下一页」→ AI 基于前一页的画风和角色外观，生成下一页 9 张分镜图

**辅助功能**
- 批量下载：用户点击「下载全部」→ 系统将当前页 9 张图打包为 ZIP 下载
- 历史浏览：用户通过页面导航 → 切换查看已生成的历史页面

## UI 布局

### 整体布局
左右两栏布局，左侧输入区占 40%，右侧输出区占 60%。

### 左侧 - 输入区
- 顶部：项目名称输入框
- 剧本输入：多行文本框，placeholder「请输入剧本内容...」
- 角色设定区：
    - 角色卡片列表，每张卡片包含：角色名、外观描述、参考图上传

- 页面导航：显示当前页数，支持切换查看历史页面

## 用户使用流程

### 首次生成
1. 输入剧本内容
2. 添加角色：填写名称、外观描述，上传参考图
3. 添加场景：填写名称、氛围描述，上传参考图（可选）
4. 选择画风
5. 点击「生成分镜」
6. 在右侧查看生成的 9 张分镜图
7. 点击「下载全部」保存

### 连续生成
1. 完成首次生成后
2. 点击「继续生成下一页」
3. AI 基于前一页的画风和角色外观，生成下一页 9 张分镜图
4. 重复直到剧本完成

## AI 能力需求

## 技术方向

| 维度 | 选择 | 理由 |
|------|------|------|
| 产品类型 | Web | 创作工具，需要方便分享和协作，无需系统权限 |
| 推荐技术栈 | Next.js + TypeScript + Tailwind | 全栈框架，支持 API 路由调用 AI 服务，SSR 利于 SEO |
| 代码组织策略 | feature-first | 新 Web 项目默认按功能收口；路由壳留在 `src/app`，业务进入 `src/features/*`，共享能力进入 `src/shared/*`，基础设施进入 `src/core/*`，避免把逻辑摊平到顶层目录 |
| 数据存储 | 本地（LocalStorage） | MVP 阶段无需登录，降低复杂度 |
| 部署方式 | 静态托管（Vercel） | 零运维，自动部署，免费额度够用 |

## 测试与验证策略

| 项目 | 设定 | 说明 |
|------|------|------|
| 默认策略 | 严格 TDD | 角色卡片校验、分镜分页、下载打包及其他新增或改变的可观察行为全部走 RED-GREEN-REFACTOR |
| RED | 先写最小测试并运行，确认因目标行为缺失而失败 | 测试通过、报错或失败原因不符时不得实现 |
| GREEN | 只实现让当前测试通过的最小行为，并运行相关回归 | 当前测试和相关回归全部通过后才算 GREEN |
| REFACTOR | 全绿后才整理生成链路、命名或重复逻辑 | 整理不得新增行为，整理后继续全绿 |
| 例外审批 | 初版原型、生成代码或配置文件如需例外，先请求用户明确批准 | 记录批准范围、替代验证、风险和恢复方案；视觉人工验收不能自行替代 RED |
| 完成证据 | 本轮 RED 失败命令与摘要、GREEN 通过命令与结果、编译和关键路径证据 | 没有 fresh RED/GREEN 证据不能说完成 |

- **文件导出**：支持 PNG 格式批量下载，打包为 ZIP 文件
```

## 写作要点

1. **产品概述**：
   - 一句话说清楚是什么
   - **必须明确写出目标用户**：是谁、有什么特点、什么痛点
   - 核心价值：用了这个产品能得到什么
   
2. **应用场景**：
   - 具体的人 + 具体的情况 + 具体的用法 + 解决什么问题
   - 场景要有画面感，让人一看就懂
   - 放在功能需求之前，帮助理解产品价值

3. **执行语境**：
   - 明确写出这是 `vibe` 还是 `standard`
   - `vibe` 默认适用于新手 / 单人 / 原型 / MVP / 先跑通场景
   - 写清楚默认时间尺度和成功标准，方便后续 Skill 继承

4. **功能需求**：
   - 分「核心功能」和「辅助功能」
   - 每条格式：用户做什么 → 系统做什么 → 得到什么
   - 写清楚触发方式（点击什么按钮）

5. **术语与命名规范**：
   - 至少列出核心对象、页面、状态或动作里的主名
   - 写清楚禁用别名，避免以后文档和代码各说各话
   - 给出代码命名映射，让后续开发不用边写边猜

6. **UI 布局**：
    - 先写整体布局（几栏、比例）
    - 再逐个区域描述内容
    - 控件要具体：下拉框写出所有选项和默认值，按钮写明位置和样式

7. **用户流程**：分步骤，可以有多条路径

8. **AI 能力需求**：
    - 列出需要的 AI 能力类型
    - 说明具体用途
    - **写清楚在哪个环节触发**，方便开发理解调用时机

9. **技术方向**：
    - 产品类型 + 推荐技术栈 + 理由，用表格呈现
    - 必须写 `Platform Profile / Language Adapter / Architecture Profile / Scaffold Policy`
    - `Scaffold Policy = template` 只用于明确匹配 Web / Desktop / Node CLI 的新项目
    - Backend、Library、Mobile、非 Node CLI 写 `platform-default` 或 `existing-incremental`，不暗示会生成 JS / TS 模板
    - 新增 `代码组织策略`：新 Web / Desktop 项目默认 `feature-first`，已有项目默认 `legacy-incremental`
    - 理由必须写清楚为什么选这个策略，不能只填一个名字
    - `feature-first` 要明确写出 `src/features/* + src/shared/* + src/core/*` 的收口方式
    - `legacy-incremental` 要明确写出“不强改旧结构，但新增业务优先局部 feature 化”
    - 如果不是 Web / Desktop，可以写“平台默认结构”，但必须解释为什么不套用本轮策略
    - 数据存储方式和部署方式也写进表格
    - 这是给 dev-planner 和 dev-builder 的输入

10. **测试与验证策略**：
    - 默认写成严格 TDD，不把顺序留给实现阶段临时猜
    - 除 visual-only T1 受控例外外，所有新功能、bug 修复、重构和行为变更都写清 RED 测试与预期失败原因、GREEN 最小实现边界、全绿后的 REFACTOR 范围
    - 受控 T1 仅限边界核对通过且无既有 seam 的同一组件 / 容器呈现微调，必须写清 seam 结论、改前基线、改后同路径证据、副作用检查与越界停止条件
    - 原型、生成代码或配置文件的例外必须记录用户明确批准、替代验证、风险和恢复方案；无法自动化本身不构成例外资格
    - 严格 TDD Task 的本轮 RED/GREEN/回归必须落盘；受控 T1 Task 的边界、seam、基线、同路径证据和副作用检查必须落盘
    - “人工验收”和“人工验收记录”必须落盘，不能把需要用户真实点击的验收留在聊天里

11. **接口契约治理**：
    - 新项目默认生成 `docs/接口契约.md`
    - 同一业务能力只能有一个统一契约入口
    - 新增或修改真实接口前，必须先登记或更新契约台账
    - 如果没有接口，也要写清“暂无业务接口”，避免后续实现阶段临时脑补

12. **技术说明**（可选）：
    - 外部服务依赖、特殊要求
    - 只在有技术约束时写，没有就不写

13. **补充说明**：用表格，适合解释选项、状态、逻辑
