[任务]
    规则淘金：扫描规则来源，做两件事——①**放错纠正**：找出写错位置的规则（项目专属规则误写进通用区、通用规则误写进项目专属区），列给用户选正确归属；②**通用回流**：找出适合"所有项目通用"的规则，AI 按第一性原理重新措辞后，经用户逐条确认，写进 vibe-coding-skills 源码（`tools/init-target-runtime.mjs` 的 Agent 宪法），清理原地并刷新目标项目文档。
    **半自动铁律**：本 Skill 只做"发现 + 重措辞 + 提议"，任何写入 vibe 源码、修改用户全局、清理原地规则的动作，必须逐条经用户明确确认后才执行；用户跳过的不再重复提议。
    **分期范围**：
    - 第一期（已落地）：手动触发、现扫现提议的"放错纠正 + 通用回流 + 宪法规则人工复核退役"。"出现处数"仅指本次现扫在几处命中，非跨会话累计。宪法规则退役走 [宪法规则退役（人工复核）]，是**人当场逐条判定**的降级，不依赖自动计数。
    - 第二、三期（未落地）：自动触发计数器、基于跨会话冷热数据的自动退役候选。第一期的人工复核版是它们上线前的兜底，也是万一"AI 自动报账"实测不可靠时的长期退路。

[与 evolution-engine 的互斥边界]
    本 Skill 与 `evolution-engine` 职责不重叠、不双写：
    - `evolution-engine`：只处理 `.claude/feedback/` 里 feedback 文档驱动的"规则毕业"（occurrences≥3 → 毕业到某 SKILL.md 或**本包自身** CLAUDE.md 的总体规则区）；不读规则扩展区、不改 `init-target-runtime.mjs` 源码。
    - `rule-harvester`（本 Skill）：只处理规则**文本本身**的归位与回流——扫目标项目的规则扩展区 + 用户全局，回流进 `init-target-runtime.mjs` 的 Agent 宪法；不读 feedback、不做 feedback 毕业。
    - 二者提到的"CLAUDE.md"不是同一份：evolution-engine 指**本包自身**的 CLAUDE.md 总体规则；本 Skill 只碰**目标项目**的 CLAUDE.md/AGENTS.md（且只读扫描其手写区、经确认才由 runtime 刷新，不手改 managed block）。

[本包治理继承]
    创建或执行本 Skill 时必须继承本包主控纪律：
    - 先判定 `execution tier`：本 Skill 会**修改 vibe-coding-skills 源码**（公共底座）并触发 runtime 刷新，属 T3+ hazard mode——写入前须列出将改哪个文件、影响面（所有用该包的项目）、可回滚方式（见 [第一性原则] 备份门），经用户确认。
    - 目标项目生命周期文档先读 `.vibe-docs.json`，再按角色映射读写四字中文 `.md`；不擅自手改 managed block（改 Agent 宪法只能改源码再刷新）。
    - 需要用户拍板"这条放哪 / 提不提拔 / 措辞对不对"时输出待确认清单；只有用户明确确认后才执行写入。
    - 本 Skill 不新增 endpoint/service/schema；不涉及 UI；不涉及 `.pen`。
    - references 采用 progressive references：先读本 `SKILL.md`，只在 [按需加载 references] 命中时读取对应 reference。

[第一性原则]
    **回流必重措辞**：写进 vibe 源码的规则绝不照抄用户原话（用户表达可能不规范、有歧义）。必须按第一性原理重新起草：目标明确、无歧义、可判定、与既有 Agent 宪法风格一致（`- 名称：正文` 单行条目）。重措辞后连同原文一起给用户看，确认"意思没跑偏"；用户要求改措辞后，须再给一次"原文 → 新措辞"对照、二次确认才可写入。
    **不做智能价值判断，只做机械识别 + 语义初筛 + 用户终审**：判断"含项目名/产品名/组件名"可机械识别（比对 `.vibe-docs.json` 的项目/产品/术语名）；但"是否通用工程纪律 vs 是否个人偏好"本质是**语义判断、可能误判**，AI 只给初筛提议 + 理由，**最终以用户逐条核对理由为准**，不得用"机械判断"话术诱导用户盲从。
    **写公共底座前先亮影响面 + 备份门**：改 `init-target-runtime.mjs` = 改所有项目的底座。每次写源码前必须：①确认该文件在 git 版本控制下（可 `git revert`）或先复制一份备份；②告知用户"这会影响所有用本包的项目、需各项目重跑刷新才生效"。缺备份/版控保障则停止写入、先告知用户。
    **升级只加不减**：本期只做提拔升级（加规则到 vibe），不做降级删除。唯一的删除动作是回流成功后"清理原地那一条"，必须按 [清理原地安全协议] 执行，绝不误伤相邻内容。发现疑似过时规则只记录提示、不删。
    **证据可复核**：提议里每条标清"来自哪个文件哪一行 / 现扫命中几处 / 重措辞前后对照"，让用户能核。

[全局来源红线]
    用户全局（`~/.claude/CLAUDE.md`、`~/.codex/AGENTS.md`）是敏感区，本包铁律禁止自动修改全局 `.claude/` / `.codex/`。因此：
    - 全局**只可只读扫描**（找出其中"其实该进 vibe 通用"的回流候选）。
    - **绝不自动写入或删除全局**——包括回流后的"清理原地"：若某条回流规则的原文位于用户全局，回流写入 vibe 后**只提示用户手动删全局那条，绝不自动删**。
    - `~/.codex/AGENTS.md` 与 `~/.claude/CLAUDE.md` 是两个不同产品的配置，分别对待、不混、不互拷。
    - 注意：一条规则回流进 Agent 宪法后，会**同时**出现在所有项目生成的 CLAUDE.md（Claude）与 AGENTS.md（Codex）两个产品块里。故回流确认时须提示用户"此规则将同时对 Claude 与 Codex 生效，请确认它对两个运行时都成立；只对单一运行时成立的应归用户全局、不回流"。

[清理原地安全协议]
    回流成功后清理"原地那一条"是唯一删除动作，必须守：
    - **全局豁免**：原文在用户全局 → 不删，只提示用户手动清理（见 [全局来源红线]）。
    - **删前预览**：把"将删除的确切文本（起止行）"展示给用户，用户确认后才删。
    - **精确匹配**：按完整条目文本匹配删除，不按模糊关键词；条目跨多行或与相邻内容粘连时，只删该条目、保留相邻用户内容。
    - **删后给 diff**：清理后展示 diff，让用户核对没误伤。
    - **失败不静默**：若源码已写入成功、但原地文本没匹配上（未删净），必须报告"源已提拔、原地未清，请人工核对 <文件:行>"，不留半删状态也不假装成功。

[宪法规则退役（人工复核）]
    这是"降级/淘汰"的第一期落地：对写进 vibe 源码 Agent 宪法的规则，找出"疑似过时/该退役"的，经用户逐条拍板后退役。**只做人工复核，不依赖自动计数**（自动冷热计数是第二、三期）。
    **地基（身份证 + 护栏）**：
    - 每条宪法规则的身份证与护栏档位登记在 `tools/constitution-rules.mjs`，与正文一一对应，由 `tools/check-constitution-rules.mjs` 双向校验锁死（正文增删改名规则却没同步登记表 → 校验 FAIL）。
    - 护栏三档：`protected`（生死线/安全/基础设施，永不退役）、`background`（呼吸级根本纪律如沟通习惯，AI 无感遵守、几乎不会主动报账，**不参与退役排名、不列候选**，防系统性少报误杀）、`candidate`（功能性/情境性规则，唯一可进退役池的档）。
    **三层护栏（防误杀，缺一不可）**：
    1. 档位护栏：只有 `candidate` 档进退役池；`protected` / `background` 碰都不碰（用 `candidateRuleIds()` 取池）。
    2. 呼吸级隔离：`background` 单独归类、不上称——它们被无感遵守，靠"是否被报账/是否高频出现"判断必然系统性偏低，一律不列候选。
    3. 人终审：退役只出候选、只做建议，用户逐条拍板才退；用户跳过的不再重复提议。数据/理由不足就不出候选。
    **退役 = 从 vibe 源码删除该规则**，属改公共底座（影响所有项目），是 T3+ hazard：必须守 [第一性原则] 备份门 + [清理原地安全协议]（删前预览确切文本、精确匹配、删后给 diff、失败不静默）。删除后同步：升 `BLOCK_VERSION`（整批退役一次性 +1）→ 从 `constitution-rules.mjs` 登记表移除对应条目 → 跑 `check-constitution-rules.mjs` 必须 PASS → 对目标项目重跑 `--write` 刷新 → `--check` 验证 → 告知用户所有项目需各自重跑刷新才生效。
    **退役理由来源（本期人工，非自动）**：现扫时结合"该规则领域是否与本项目相关（比对 `.vibe-docs.json`）、是否长期未在项目中体现、是否已被更强规则取代"给出**候选 + 理由**，明确标注这是 AI 语义初筛、最终以用户核对理由为准，不得用"机械判断"话术诱导盲从。

[归类判据]
    判断一条规则"该放哪"：
    - **项目专属**（该在《宪法设计.md》手动扩展区）：含具体项目名/产品名/组件名/业务对象、只在本项目成立的约定 → 可机械识别（比对项目名）。
    - **本项目通用但跨 AI**（该在 Agent 宪法，经 vibe 源码）：任何项目都适用、不含具体项目名的工程/流程/沟通纪律 → 通用性靠 AI 语义初筛，可能误判，用户终审。
    - **个人私人/特定运行时**（该在用户全局）：只对某运行时成立（如某 AI 的特定工具用法）、或纯个人偏好，跨项目但不该进分发给别人的技能包。
    - **放错** = 规则实际位置 ≠ 判据指向位置。列出"现在在哪、判据认为该在哪、理由"，让用户核理由后拍板。

[各来源的扩展区定位方法]
    - 目标项目《宪法设计.md》：定位文末 `## 手动扩展区` 标题（本包 target-constitution 生成的宪法设计约定此标题）之下的条目为可淘金区；若该项目宪法设计无此标题，则报告"未找到手动扩展区标记"，跳过该来源、提示用户。
    - 目标项目 `CLAUDE.md`/`AGENTS.md`：以 `<!-- vibe-coding-skills:target-runtime:start ... -->` 和 `<!-- vibe-coding-skills:target-runtime:end -->` 两个标记为界，标记**之前**与**之后**的内容都是用户手写区，都要扫；标记之间是 managed block，只读不动。
    - 用户全局两份：整份只读扫描（守 [全局来源红线]）。

[工作流程]
    [第一步：确认 skills root 与目标项目]
        定位 vibe 源码根与目标项目根。
        完成条件：拿到 `tools/init-target-runtime.mjs` 路径 + `.vibe-docs.json` 路径（缺 skills root 则回流不可用、只做放错纠正并告知）。

    [第二步：按 [各来源的扩展区定位方法] 扫描三处来源]
        完成条件：得到三处规则条目清单（含来源文件+起止行）；无法定位的来源明确标注跳过原因。

    [第三步：机械识别 + 通用语义初筛]
        对每条按 [归类判据] 判"应属位置"、标出"放错"、标出"回流候选"，记现扫命中处数。
        完成条件：产出"放错清单"+"回流候选清单"，每条附来源、理由（区分机械识别 vs 语义初筛）。

    [第四步：重措辞（仅回流候选）]
        按 [第一性原则] 重措辞成无歧义、合 Agent 宪法风格的条目。
        完成条件：每条给出"原文 → 重措辞后"对照。

    [第五步：生成待确认提议，逐条等用户拍板]
        按 [提议格式] 输出。放错项让用户选归属；回流项让用户确认"提拔+措辞"（含 [全局来源红线] 的双运行时提示）。用户要求改措辞的，改后再给对照、二次确认。
        完成条件：用户对每条给出 确认/跳过/改措辞；改措辞项已二次确认。

    [第六步：执行已确认项]
        - 放错纠正：把规则移到用户选定的正确文件（项目内文件可自动移；**全局只提示手动**）。
        - 通用回流（守 [第一性原则] 备份门）：①确认源码可回滚/先备份 → ②把重措辞后的规则写进 `init-target-runtime.mjs` 的 Agent 宪法**对应 `### 分组`**（无匹配分组时向用户提议新建分组或归入最贴近的一组，经确认）→ ③升 `BLOCK_VERSION`（整批回流一次性 +1）→ ④按 [清理原地安全协议] 清理原地 → ⑤对目标项目重跑 `--write` 刷新 → ⑥ `--check` 验证 → ⑦跑 markdown 治理检查。
        - 全程每个写入动作前复述"要改什么"，改后给证据/diff。
        完成条件：check + 治理检查 PASS；被移动/提拔的规则原地已按协议清理（或如实报告未清项）；向用户报告改了哪些文件、影响面、其他项目如何同步（各自重跑刷新；其他项目若有同条手写规则，刷新后会与块内重复、需各自手动清理）。
