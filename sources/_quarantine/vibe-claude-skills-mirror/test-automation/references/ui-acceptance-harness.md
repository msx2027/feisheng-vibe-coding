# ui-acceptance-harness

[读取时机]
    UI / Electron 验收脚本重复包含启动、等待、点击、截图、DOM / 滚动条检查、report 输出或进程清理样板逻辑时读取。

[目标]
    把重复的 UI 验收脚本样板收敛为目标项目内的 UI 验收工具箱，让每轮验收脚本只描述本次场景、动作和断言。

[触发条件]
    - 同一目标项目第二次出现类似 UI / Electron 验收脚本。
    - 单个脚本里已经重复写出启动应用、等待页面、点击按钮、截图、DOM 查询、滚动条检查、report 写入或进程清理。
    - 验收报告需要稳定复用截图路径、窗口尺寸、断言结果和人工验收状态。

[允许内联]
    - 一次性、低风险、不会形成回归入口的临时 UI 检查可以内联。
    - 项目还没有 UI 自动化基础设施，且搭建工具箱成本明显高于本轮验证收益时，可以先用临时脚本，但必须记录后续抽取条件。

[抽象边界]
    UI 验收工具箱最低应封装：
    - `launch/open`：启动 Web / Electron 目标，记录进程和窗口信息。
    - `action`：点击、输入、导航、菜单或键盘操作。
    - `wait`：等待页面 ready、关键选择器、网络空闲或 Electron 窗口可交互。
    - `screenshot`：统一截图目录、文件命名和失败时截图。
    - `assertion`：DOM、可见性、滚动条、内部字段、布局 rect、关键文案和状态检查。
    - `report`：写入结构化验收结果。
    - `cleanup`：只清理本轮拉起的 browser、dev server、Electron 进程和临时文件。

[report 约定]
    report 可以是 JSON 或项目既有格式，但至少记录：
    - `scenario`：本次验收路径或场景名。
    - `actions`：关键用户动作和目标选择器 / 名称。
    - `assertions`：断言项、期望、实际结果和 pass / fail。
    - `screenshots`：截图文件路径、截图时机和失败截图。
    - `status`：整体 pass / fail / blocked。
    - `errors`：失败摘要、异常堆栈或阻塞原因。
    - `manualAcceptanceStatus`：`不适用`、`待用户验收`、`用户已确认` 或 `需回归复验`。
    - Electron 项目还应记录窗口尺寸或 viewport，必要时记录 device scale factor。

[Electron 注意事项]
    - 启动器必须区分本轮新拉起的进程和用户已有窗口；清理时只停止本轮进程。
    - 如果项目有 single-instance lock，验收前先识别旧实例是否会拦截新窗口，不把旧窗口截图当成 fresh 证据。
    - 窗口 ready 后再截图；截图前确认关键新字符串、路由或 DOM 标记来自当前源码。
    - 失败时保留 report、截图和启动日志，不能把“窗口打开过”包装成验收通过。

[人工验收关系]
    - UI 验收工具箱只能证明可自动化的路径、布局和状态；用户体验、设计感知、权限感知、安装启动体验等仍可能需要人工验收。
    - 自动化 report 里的 `manualAcceptanceStatus` 不得写成 `用户已确认`，除非用户已经在对话中明确确认真实点击、操作或观察过。
    - 后续改动命中已人工验收范围时，优先用工具箱补自动化回归；自动化无法覆盖时，只提醒用户复验受影响路径。

[反模式]
    - 每轮复制几十到上百行启动、等待、截图、report 样板，只改一个按钮名。
    - 工具箱提前做成跨项目平台、CLI 或生成器，而当前只需要目标项目内 helper。
    - 清理进程时杀掉用户已有 Electron / browser / dev server。
    - 只有截图没有断言，或只有断言没有失败截图和 report。
