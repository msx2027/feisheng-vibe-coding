# workflow

[读取时机]
    实际执行 audit / setup / author / run-report，或需要输出测试证据时读取。

[audit 模式]
    1. 读取 `.vibe-docs.json`、需求文档、开发计划和验收记录；缺失时进入代码发现模式。
    2. 扫描测试相关文件：package scripts、测试配置、CI workflow、`tests/`、`e2e/`、`__tests__/`、pytest / Playwright / Vitest / Jest 配置。
    3. 如果存在 UI / Electron 验收脚本，检查是否重复启动、等待、截图、DOM / 滚动条检查、report 输出或进程清理样板逻辑；命中时读取 `ui-acceptance-harness.md`。
    4. 列出现有测试命令、覆盖层级、关键路径缺口和假绿风险。
    5. 输出最小补测试建议：优先级、测试层级、目标路径、预期证据。

[setup 模式]
    1. 根据项目技术栈和现有约定选择框架；必要时读取 `framework-selection.md`。
    2. 查官方文档确认安装和配置命令。
    3. 最小新增依赖、配置、脚本和一条 smoke / 示例测试。
    4. 运行新测试命令，确认实际发现并执行测试文件。
    5. 若涉及 CI，同步 CI 命令并说明本地与 CI 的差异。

[author 模式]
    1. 明确被测行为：用户路径、API 契约、纯逻辑、bug 复现或回归范围。若主 Agent 已证明属于无既有 seam 的 visual-only T1 受控例外，不进入 author 模式，不为微调新建测试框架；回到 directed-check 并保留改前基线。
    2. 确认测试 seam 位于 public interface、统一契约或用户可观察行为边界；一个循环只覆盖一个行为。
    3. RED：先写最小测试，运行并确认它因目标行为缺失而正确失败；测试通过、测试报错或失败原因不符时先修测试，不得写生产代码。
    4. GREEN：只写让当前测试通过的最小生产代码，运行当前测试与相关回归并保持全绿。
    5. REFACTOR：仅在全绿后消除重复、改善命名或提取 helper；不得新增行为，整理后重跑测试。
    6. 复用现有 fixture、mock、临时目录和测试工具；mock 仅在不可避免时使用，不测试 mock 自身行为。
    7. UI / Electron 验收脚本第二次出现相似样板，或本轮脚本重复启动、等待、截图、DOM / 滚动条检查、report 输出和进程清理时，先复用或创建目标项目内 UI 验收工具箱。
    8. 补覆盖 happy path、关键错误态和本轮风险直接相关的回归点，避免横向铺无关分支。
    9. 无法自动化时继续建立测试 seam；仍无法形成正确 RED 就停止生产代码修改。无法自动化本身不构成例外资格。

[run-report 模式]
    1. 运行与当前风险匹配的最小测试命令。
    2. 记录命令、测试文件或用例数量、通过 / 失败结果、关键输出。
    3. UI / Electron 验收 report 至少记录场景、动作、断言、截图路径、pass / fail、失败摘要和人工验收状态；Electron 验收还记录窗口尺寸或 viewport。
    4. 失败时先保留失败摘要，不把失败包装成“基本可用”。
    5. 如果没有测试被发现，按未验证处理并修正测试路径或命令。
    6. 输出人工验收状态：`不适用`、`待用户验收`、`用户已确认`、`需回归复验`。

[收口报告]
    必须包含：
    - 测试目标和测试层级
    - 本轮 RED 测试命令、正确失败原因和失败摘要
    - 本轮 GREEN 测试命令、通过数量和相关回归结果
    - REFACTOR 后保持全绿的证据，或明确未发生 REFACTOR
    - 例外时的用户明确批准依据、范围、替代验证、风险和恢复方案
    - visual-only T1 受控例外时的改前基线、改后同路径定向视觉证据、副作用检查与边界复核
    - 自动化覆盖范围
    - UI / Electron report 的场景、动作、断言、截图和失败摘要（如适用）
    - 人工验收状态和需要用户真实点击的路径（如适用）
    - 后续回归触发条件
