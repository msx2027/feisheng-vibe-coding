# LLM 编码反模式速查

> 来源：code-review/SKILL.md 的 [按需加载 references]。
> 读取时机：审查实现纪律、过度抽象、静默假设、顺手重构或验证目标不清时。

[定位]
    本文件把常见 LLM 编码失误改写成本项目的审查判据。
    它不新增路由，不替代 `review-dimensions.md`，只在需要判断“实现纪律”时提供更具体的反模式清单。

[四类反模式]

    1. 静默假设
        表现：
        - 需求有多种合理解释，代码直接选了一个方向实现
        - 未说明字段、范围、权限、数据量、格式、路径、默认值等关键假设
        - 用户前提、Spec、实现证据冲突时，报告帮实现圆过去

        审查要求：
        - 要求实现说明假设、备选解释和为什么当前选择成立
        - 影响安全、数据、权限、接口或用户路径时，不能靠默认猜测放行
        - 高影响歧义没有澄清或证据时，按 Stage 1 问题处理

    2. 过早抽象
        表现：
        - 单次任务引入策略模式、插件层、配置系统、泛型框架或多层 adapter
        - 为未来可能性添加 option、callback、feature flag、provider 等扩展点
        - 代码量明显超过当前需求，且没有复用点或已确认的后续场景

        审查要求：
        - 先问“当前任务是否真的需要这层抽象”
        - 单次使用的抽象默认视为可疑，除非它复用已有架构或降低真实复杂度
        - 能用已有项目风格和局部函数完成时，不接受新建通用框架

    3. 顺手改动
        表现：
        - 修 bug 时顺便重排代码、改注释、换引号、加类型、重命名变量
        - 改目标功能时清理无关 dead code、移动邻近模块或重写周边结构
        - diff 中存在无法直接追溯到用户请求或当前成功标准的行

        审查要求：
        - 每一行改动都必须能说明和用户请求的关系
        - 只清理由本轮改动制造出来的 unused import、孤儿变量和破损引用
        - 发现无关历史问题时记录为后续事项，不在本轮直接改

    4. 目标不可验证
        表现：
        - 计划只写“检查 / 修复 / 优化 / 测试”，没有可判定成功的条件
        - 新功能、bug 修复、重构或行为变更没有本轮 RED 正确失败与 GREEN 通过证据
        - 功能完成只给“看起来正常 / 应该可以”，没有 fresh 验证命令或证据

        审查要求：
        - 每个成功标准都要能通过测试、命令输出、截图、日志或人工验收路径证明
        - 所有新增或改变的可观察行为都必须先有 failing/regression test，GREEN 仅做最小实现，全绿后才能 REFACTOR
        - 无法自动化时必须继续建立测试 seam 或停止生产代码修改；无法自动化本身不构成例外资格

[Priority 判定]

    - High：静默假设影响安全、权限、数据、接口、删除、支付、发布或用户不可逆路径；或无验证证据却声明完成。
    - Medium：过早抽象、顺手重构、验证目标不清导致维护成本或回归风险上升。
    - Low：表达不够清楚、示例不足、可读性细节，但不影响当前行为判断。

[报告口径]

    - 不写“建议更简单一点”这种泛泛评价。
    - 要指出具体文件、具体改动类型、为何超出需求、应删除或收窄到什么范围。
    - 如果当前实现确实需要复杂度，要求证据：已有调用方、明确后续需求、架构约束或测试收益。
