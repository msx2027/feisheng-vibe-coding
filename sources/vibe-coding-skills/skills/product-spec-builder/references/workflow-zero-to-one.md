# 工作流程（0-1模式）

> 来源：product-spec-builder/SKILL.md 的 [工作流程（0-1模式）]。
> 读取时机：新目标项目从无到有生成 Product Spec 和初始映射时。

## 目录

- 需求探索阶段
- 需求完善阶段
- 文档生成阶段
- 执行语境、测试与验证策略
- 输出文件

[工作流程（0-1模式）]
    [需求探索阶段]
        目的：让用户把脑子里的东西倒出来

        第一步：接住用户
            基于用户已经表达的内容，先 WebSearch 搜索相关竞品和市场信息
            然后直接开始追问，不重复问"你想做什么"
            如果搜到了类似产品，直接告诉用户："市面上有 XX 和 YY 在做类似的事，你觉得你的和他们有什么不一样？"

        第二步：追问
            针对模糊、矛盾、自嗨的地方，直接追问
            每次1-2个问题，问到点子上
            同时思考哪些功能可以用 AI 增强
            涉及技术/行业/竞品时，先 WebSearch 再发言

        第三步：阶段性确认
            复述理解，确认没跑偏
            有问题当场纠正

    [需求完善阶段]
        目的：填补漏洞，逼用户想清楚，确定 AI 能力需求和界面布局

        第一步：漏洞识别
            对照 [需求维度清单]，找出缺失的关键信息

        第二步：逼问
            针对缺失项设计问题
            不接受敷衍回答
            布局问题要问到具体：几栏、比例、各区域内容、控件规范
            涉及不确定的技术或方案时，先 WebSearch 搜索确认再给建议

        第三步：AI能力引导
            主动询问用户：
            - "这个功能要不要加 AI 一键优化？"
            - "这里让用户手动填，还是让 AI 智能推荐？"
            根据用户需求识别需要的 AI 能力类型（文本生成、图像生成、图像识别等）
            涉及具体 AI 能力时，WebSearch 搜索最新可用的模型和方案

        第四步：平台方向确认
            根据 [平台适配策略] 分析用户的产品特征
            给出 2-3 个平台方案 + 各自优劣
            逼用户做出选择
            选定平台后同步确认 language adapter、architecture profile、scaffold policy 和 fallback stack；未知技术栈只问一个关键问题，不静默套 Web / Node
            选定后评估技术复杂度，复杂度高的建议分期

        第五步：充足度判断
            对照 [信息充足度判断]
            「必须满足」都达成 → 提议生成
            未达成 → 继续问，不惯着

    [文档生成阶段]
        目的：输出可用的 Product Spec 文件

        第一步：整理
            将对话内容按输出模板结构分类

        第二步：填充
            加载 templates/product-spec-template.md 获取模板格式
            按模板格式填写
            「尽量满足」未达成的地方标注 [待补充]
            功能用动词开头
            UI布局要描述清楚整体结构和各区域细节
            流程写清楚步骤

        第三步：识别AI能力需求
            根据功能需求识别所需的 AI 能力类型
            在「AI 能力需求」部分列出
            说明每种能力在本产品中的具体用途

        第四步：填写技术方向
            根据对话中确认的平台方向和技术评估
            填写「技术方向」部分：产品类型、推荐技术栈、Platform Profile、Language Adapter、Architecture Profile、Scaffold Policy、代码组织策略、核心理由
            - 如果是新 Web / Desktop 项目 → 默认写 `feature-first`，并说明路由壳留在框架目录、业务进入 `src/features/*`、共享进入 `src/shared/*`、基础设施进入 `src/core/*`
            - 如果是已有项目迭代 → 默认写 `legacy-incremental`，并说明不强改旧结构，但新增业务优先局部收进 feature 模块
            - 如果不是 Web / Desktop → 在理由里明确写“沿用平台默认结构”的原因，不强行套入本轮模块化改造
            - 如果是 Backend / Library / Mobile / 非 Node CLI → `Scaffold Policy` 写 `platform-default` 或 `existing-incremental`，不使用现有 JS / TS 模板
            - 无论选哪种策略，都必须写“为什么”，不能只填一个名字

        第五步：填写术语与命名规范
            根据对话中确认的核心对象、页面、状态和动作
            按严格注册表填写「术语与命名规范」部分（禁止使用宽松列）
            用户是小白时，先把大白话归纳成主名，再补代码命名映射和禁用别名
            新增主名、替换旧名或收敛别名时，必须写进文档，不留在聊天里

        第六步：填写执行语境
            根据对话中确认的用户类型、协作方式、默认时间尺度和成功标准
            填写「执行语境」部分
            如用户没有显式声明但符合 [执行语境优先原则] 的 `vibe` 信号 → 明确写成 `交付模式 = vibe`

        第七步：填写测试与验证策略
            根据对话中确认的可观察行为、回归风险和用户期望
            填写「测试与验证策略」部分
            不满足 visual-only T1 受控例外且用户没有显式批准文件类型例外时 → 明确写成 `严格 TDD / RED-GREEN-REFACTOR`
            写清楚：
            - 每个行为的 RED 测试、运行命令和预期失败原因
            - GREEN 最小实现边界与相关回归命令
            - 全绿后的 REFACTOR 范围
            - 原型、生成代码或配置文件的用户批准状态；无法自动化本身不构成例外资格
            - 本轮 RED 与 GREEN 完成证据

        第八步：输出文件
            将 Product Spec 保存为 `需求文档.md`
            创建或更新 `.vibe-docs.json`，写入默认文档角色映射
            如果目标项目尚无 `验收记录.md`，加载 templates/manual-acceptance-template.md 并创建初始人工验收记录文档
            如果目标项目尚无 `接口契约.md`，创建初始接口契约文档；即使第一版暂无真实接口，也登记“暂无业务接口”初始行
            运行 `tools/check-target-doc-names.mjs <目标项目根目录> --require-existing` 校验四字中文 `.md` 命名
