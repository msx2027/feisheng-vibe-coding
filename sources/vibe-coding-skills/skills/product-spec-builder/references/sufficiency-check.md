# 信息充足度判断

> 来源：product-spec-builder/SKILL.md 的 [信息充足度判断]。
> 读取时机：判断需求是否足够落盘，是否能生成 `需求文档.md`。

[信息充足度判断]
    当以下条件满足时，可以生成 Product Spec：

    **必须满足**：
    - ✅ 产品定位清晰（能用一句人话说明白这是什么）
    - ✅ 目标用户明确（知道给谁用、为什么用）
    - ✅ 核心功能明确（能说清楚产品必须有什么功能、为什么需要）
    - ✅ 用户流程清晰（至少一条完整路径，从头到尾）
    - ✅ AI能力需求明确（知道哪些功能需要 AI，用什么类型的 AI）
    - ✅ 产品类型确定（Web / Desktop / CLI / Mobile / Backend / Library / Agent）
    - ✅ 技术栈 Profile 明确（知道 platform profile、language adapter、architecture profile、scaffold policy 和 fallback stack；未知技术栈已提出关键确认问题）
    - ✅ 执行语境明确（知道是 `vibe` 还是 `standard`，以及默认时间尺度）
    - ✅ 代码组织策略明确（知道为什么选 `feature-first`、`legacy-incremental`，或为什么沿用平台默认结构）
    - ✅ 术语与命名规则明确（核心对象有统一口径、禁用别名和代码命名映射）
    - ✅ 严格 TDD 策略明确（除 visual-only T1 受控例外外，每个新功能、bug 修复、重构和行为变更都有 RED、GREEN、REFACTOR 与本轮证据要求；受控 T1 有边界核对、既有 seam 结论、基线、同路径证据与副作用检查，其他例外有用户明确批准）
    - ✅ 需求澄清门已通过（影响行为、验收、数据、权限、接口或范围的歧义均已在“需求澄清记录”决策；没有 `未决 / blocked` 项）

    **尽量满足**：
    - ✅ 整体布局有方向（知道大概是什么结构）
    - ✅ 控件有基本规范（主要输入输出方式清楚）

    如果「必须满足」条件未达成，继续追问，不要勉强生成一份垃圾文档。
    如果「尽量满足」条件未达成，可以生成但标注 [待补充]。
